# Desktop

Electron's main process for the Mac app. The office the window shows is the Vite client, not this directory.

- `tsconfig.desktop.json` typechecks this directory (Node types, no DOM) and emits `dist/desktop`. Relative imports end in `.js`. `package.json` `"main"` is `dist/desktop/main.js`.
- The window loads the office page with `sandbox: true` and `contextIsolation: true`. Office UI stays in `src/client`.
- `app.setPath('userData', …/com.nikships.droid-office)`. The default `Droid Office` folder belongs to the Unity office.
- `office.ts` starts `bin/droid-office.js` on Electron's Helper binary (`runtime.ts`) with `ELECTRON_RUN_AS_NODE=1`, in the login shell's environment (`shell-path.ts`), not just its `PATH`. Quitting sends that process SIGTERM, which keeps workers and PTYs. A script the office itself runs with `process.execPath` still goes through `runAsNode` in `src/server/workers.ts`.
- Closing the window, Cmd+Q included (**Close to Menu Bar**), leaves the app running as a menu bar icon (`tray.ts`; the pure menu, its status lines and what each state allows are `tray-model.ts`, tested in `tests/desktop-tray.test.ts`). `main.ts` hides the Dock icon then, and `windowWanted` keeps a restart or a crash from opening the window again. Only `before-quit` stops the office, and every real quit comes through it (the menu bar's Quit, Option+Cmd+Q, the Dock, logout, shutdown, an update): never turn one of those into a close. `tray-icon.ts` is written by `tools/tray-icon.py`; run that instead of editing it.
- The app has one window in one of two modes, `settings.mode` (`office`: the presenter; `companion`: `/dashboard` in an ordinary `BrowserWindow`, `companion.ts`). Never open both, never add a second window or a per-mode menu item: the menu bar and the Office menu have a single Switch (`switchMode` in `main.ts`, label `switchLabel` in `tray-model.ts`), and `officePage()` is the only place that maps a mode to a URL. A window that is switched away from is detached (`win = undefined`), taken out of full screen (`leaveFullScreen` in `full-screen.ts`, tested in `tests/desktop-full-screen.test.ts`) and only then closed, before the other mode's window opens: opened while macOS is still on the old full-screen Space, the presenter's every-Space page window keeps that Space as an empty black one.
- `updates.ts` installs the zip named by this repository's public `latest-mac.yml` (electron-updater, Squirrel.Mac). The update has to be signed by the same Developer ID. The whole update flow is one window (`update-window.ts`); add a state as a phase in `update-view.ts` (pure, tested in `tests/desktop.test.ts`), not as another `dialog`.
- A preload is `.cts` (it emits `.cjs`): sandboxed preloads can't be ES modules. `tsconfig.desktop.json` includes `*.cts`.
- Startup fails loud, never degraded. `requirements.ts` (pure, tested in `tests/startup-requirements.test.ts`) decides whether this is macOS 14+ on Apple silicon with a Pro, Max or Ultra chip; `startup.ts` reads the machine and `failStartup(failure)` shows the dialog (or, with `--startup-check`, prints to stderr), appends to `startup.log` and quits. Wording lives in `startup-failure.ts`. The native module and shared-texture code report their errors through `failStartup(nativeModuleFailure(err))` / `failStartup(sharedTextureFailure(why))`; `failStartup` throws `StartupAborted`, which `main.ts` swallows. Keep `MIN_MACOS` / `MIN_DARWIN` in step with `mac.minimumSystemVersion` in `electron-builder.yml`. `DROID_OFFICE_ALLOW_ANY_CHIP=1` skips only the chip check and is for CI's base-chip VMs; don't use it to make a local run pass on a Mac that isn't Pro or better.
- `--user-data-dir=<folder>` moves `userData` and the logs, and `--startup-check` runs the gates with no window and exits. A test run of the packaged app uses both so it never touches the installed app's lock, settings or logs.
- Packaging is `electron-builder.yml`: `asar: false`, `npmRebuild: false`, arm64, hardened runtime, entitlements in `build/`. `npm run desktop` runs the checkout. `npm run package:mac` writes `release/`. `npm run build` ends with `build:native` (`native/build.mjs`: node-gyp on `native/presenter`, macOS only, Node-API so no Electron headers); `files:` ships only `native/presenter/build/Release/presenter.node`, which electron-builder signs with the app and `native.ts` loads by path. A native file that has to be loaded at runtime goes in `files:` and gets signed the same way; `release.yml` checks the presenter's architecture, minimum macOS, signature and load. Notarizing needs `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID`.
- `browser.ts` runs `droid-office browser install` on the same Helper binary at every launch, in the background and never fatal, so the Whiteboard's Chromium is downloaded on first launch and again when an update pins a new revision. The browser lives in the folder `src/server/whiteboard-browser.ts` (`browsersPath`) names, shared with source checkouts, not in `userData`. `playwright-core` ships inside the app as a normal dependency (no asar), and its bundled CLI does the download.
- Input: the window shows the offscreen page through `native/presenter`, so nothing arrives at the page by itself. `input_view.mm` turns AppKit events into plain dictionaries, `presenter-input.ts` (`PresenterInput`, tested over fakes in `tests/presenter-input.test.ts`) turns those into `sendInputEvent` / CDP calls, and the pure pieces (`input-events.ts`, `input-keys.ts`, `input-lock.ts`, `input-bridge.ts`, `input-cursor.ts`, `edit-menu.ts`) are tested in `tests/input-events.test.ts` without Electron. Keep them free of `electron` imports.
- The window's content view is Electron's `BridgedContentView`, whose hit test answers itself for any subview it did not host, so AppKit never gives `DOPresenterView` a click, drag or scroll by itself (hover works, because tracking areas ignore hit testing). `input_view.mm` installs a local event monitor (`routed:`) that hands the presenter view the mouse and scroll events the content view took, and only re-takes first responder for keys; the title bar, traffic lights and resize edges stay the frame's. Synthesized events that go straight into the view skip all of this, so a check of clicks has to post them through the event queue (`NSApp postEvent:`), and `tests/presenter-native-input.test.ts` guards the monitor's shape.
- The page is untrusted. Its only way to the main process is the CDP binding `__droidOfficeHost` (`input-bridge.ts`): a fixed set of messages (`lock`, `exit`, `escUp`, `editable`), each at most 512 bytes and validated, accepted only from the office's main frame in its default world at the office's origin (`trustedContext`). A new message is a new line of the allowlist, a parser branch with a test, and an entry in the guide. Never pass the page's data to a file, a shell, a URL or the native module without validating it; never expose the native module or `electron` to the page.
- The injected page script is `page/shim.ts`, a real source file with its own `tsconfig.desktop-page.json` (DOM types, no imports, emitted to `dist/desktop/page/shim.js`, which `build:desktop` and `typecheck` cover). It implements pointer lock (Chromium refuses it offscreen), the `<select>` list, `title` tooltips and the caret report. Behavior it must keep for `src/client/player.ts`: the events, `pointerLockElement`, the promise (rejecting `NotSupportedError` for `unadjustedMovement` without a raw mouse), Esc and relock rules (#195). The rules are in `input-lock.ts`; change them with its tests.
- Attach the DevTools Protocol to the offscreen page only after `did-finish-load` of a first page: `Runtime.enable` hangs before the first commit. `PresenterInput` does this and re-injects the shim for every new document with `Page.addScriptToEvaluateOnNewDocument`.
- Visibility belongs to `presenter.ts` (`PresenterWindow.setVisible`). Input code never shows, hides or focuses the page's window itself: it focuses `contents` and turns on CDP focus emulation (`Emulation.setFocusEmulationEnabled`) so `document.hasFocus()` follows the visible window. Don't call `webContents.invalidate()` on the offscreen page (it hangs).
- The Edit menu is `edit-menu.ts` and acts on `win.contents`: `BaseWindow` has no `webContents`, so a menu role would do nothing. Do not replace it with `{ role: 'editMenu' }`.
- A page that crashes or a window that can't draw must never leave a frozen or black window. `presenter-recovery.ts` (pure, `tests/presenter-recovery.test.ts`) holds the policies `presenter.ts` applies: reload the page once on a render-process crash and ask after a second within a minute, reload once when the GPU process dies and the page stays silent for 3 s, and show the window only once the addon reports a drawn frame (`firstDrawn`) so an import failure ends in `failStartup`. A window the page opens is never an Electron window (`windowOpenAction` sends it to the browser): a child of the offscreen page would inherit shared-texture rendering with nothing to show it. The page's IPC is accepted only from its main frame at the office's origin (`trustedFrame`). After the navigation to the office, Electron's offscreen view sometimes starts with no paint events reaching the presenter (the page runs, the window keeps the splash); `PaintStall` kicks it (stop then start painting), reloads once, and ends in `failStartup` about 9 to 10 s after the page loaded (an app-started reload sets `PresenterWindow.reloading` so the "Leave the office?" prompt in `main.ts` stays quiet), so keep that watch armed on every load of the office origin and never on the splash (a cold first launch can sit on it for 20 s).
- Nothing in the presenter may outlive the offscreen page. Quitting closes and destroys the page before the visible window's `closed`, so a timer or event that reaches `contents` then raises "Object has been destroyed" as an uncaught exception in the main process. Every presenter timer goes through `PresenterTimers` (`presenter-lifecycle.ts`), and `PresenterWindow.quiesce()` stops them all, stops `InputFrameRate` and calls `onGone` (which stops `PresenterInput`) on `before-quit`, the page window's `close` and the contents' `destroyed`. A call on the page goes through `onPage` or checks `gone()`; `PresenterInput` drops every event, visibility change and protocol call once `stop()` has run, and wraps the calls a destroyed page throws on. A new timer or listener in the presenter takes the same path, with a test (`tests/presenter-lifecycle.test.ts`).
