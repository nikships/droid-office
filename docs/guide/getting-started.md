# Getting started

## Requirements

For the production Mac app:

- **macOS 14 (Sonoma) or later, on a Mac with an Apple M-series Pro, Max or Ultra chip** (M1 Pro and later; no Intel Macs, no base M1 to M5). The app is arm64-only and draws through a native Metal presenter that needs macOS 14. A 120 Hz ProMotion display, with HDR where the display supports it, is what it is tuned for. It checks the macOS version and the chip at launch and quits with a message on anything else (see [The Mac app](#the-mac-app)). The app includes its own Node.js runtime; no separate Node.js install is needed.
- The **[Droid CLI](https://docs.factory.ai/cli/getting-started/quickstart)** (`droid`), Factory's coding agent, signed in to a Factory account as the user that runs the office. Every worker and board agent is a Droid session. You don't need it beforehand: when it's missing or signed out, the office opens [the welcome](#the-welcome), which installs it and runs its sign-in, where you sign in to Factory or create an account.
- **Optional: a Claude or ChatGPT subscription.** On a Mac, workers can run on the Claude or ChatGPT plan you already pay for (and a few others) through [DroidProxy](https://github.com/nikships/droidproxy), a small menu-bar app the office installs and drives for you (see [Subscriptions](models-and-prompts.md#subscriptions)).
- **git**, plus the **GitHub CLI** (`gh`) logged in (`gh auth login`) for GitHub projects' issue and PR boards, and the **GitLab CLI** (`glab`) logged in (`glab auth login`) for GitLab projects. A GitLab floor's PR board shows its merge requests, and its workers open merge requests with `glab`. Self-managed GitLab instances work once `glab auth login --hostname <host>` has signed in to them.
- **Chromium**, for the Whiteboard's renderer: about 100 MB to download and 200 MB on disk, downloaded for you (see [Chromium for the Whiteboard](#chromium-for-the-whiteboard)). The office runs without it.
- `curl` is optional. The status hooks use it when it's there and fall back to Node when it isn't.

Developer checkouts also need **Node.js 20+** and npm. On macOS, `npm run build` also compiles the native Metal presenter (`native/presenter`, with node-gyp), which needs Xcode or its command line tools; elsewhere that step is skipped. The source can run on macOS, Linux and Windows, but those checkouts are not supported production installations.

## Install & run

**The Mac app release is the only supported production install.** Download `Droid-Office-<version>-arm64.dmg` from the [latest release](https://github.com/nikships/droid-office/releases/latest), open it, and drag **Droid Office** into Applications. Launch the app to start your office. It keeps itself up to date; see [The Mac app](#the-mac-app) for first launch, logs and updates.

Command-line installers and standalone server release tarballs are no longer provided or supported. Developers can clone the repository and run or modify it themselves; see [Development](development.md).

### Running a developer checkout

To run the built source without Vite:

```bash
git clone https://github.com/nikships/droid-office.git
cd droid-office
npm ci              # builds the client, server and desktop app
npm run start       # runs the built office from this checkout
```

The command examples below use `droid-office` as shorthand for `node bin/droid-office.js` from the checkout. They are developer tools, not a production installation method.

The first time the checkout starts in a terminal, it walks you through setting up before it opens:

1. **Which folder your projects are in.** It suggests a code folder you already have (`~/Workspace`, `~/code`, `~/repos`…), else your home folder. The office looks for git projects in it and its subfolders, and never clones or copies anything.
2. **Your first project.** It lists the git projects it found, most recently active first. Pick one by number, type its full path, or type a word to search. It becomes the first floor, and you can add more the same way.

Press Enter to skip any step: the elevator in the office asks for your first project too. Run `droid-office setup` to go through it again while the office is stopped, or `droid-office setup --projects ~/Workspace --project ~/Workspace/my-project` to do the same without questions, from a script.

It prints the URL for this machine's browser, which needs no login, and — unless bound to loopback — a join URL and QR code for other devices on your Wi-Fi (see [Access](#access) below).

The office keeps its data in `~/droid-office` (`--home` or `DROID_OFFICE_HOME` to move it) and opens your existing checkouts as floors where they are. To make it look for them in another folder, like `~/Workspace`, pick the **Workspace folder** in ⚙️ Settings → **Office & floors**, or with **Change folder** in the elevator's add-a-project panel (or start with `--projects` or `DROID_OFFICE_PROJECTS`). The folder has to exist. Floors you already have stay where they are when it moves. The list of floors is `~/droid-office/.droid-office/floors.json`. Each floor keeps its workers, pictures and worktrees in its own checkout's `.droid-office/`.

Every setting the office reads from the environment is listed, with its default, in [`.env.example`](../../.env.example). The office doesn't load `.env` files: export the settings in the shell that starts it, or set them as `Environment=` lines in a developer checkout's systemd unit. A command-line flag wins over its environment variable.

You can also start the office in a project, `droid-office ~/code/my-project`: that project becomes a floor, and the office keeps its data in `~/code/my-project/.droid-office` as it did before there were floors. An office that already ran in a project carries on in it when you start `droid-office` there again. You can take that project off the building in the elevator like any other floor.

### Chromium for the Whiteboard

The Whiteboard draws its cards with a headless Chromium, driven by `playwright-core` and pinned to the revision that release expects. Its sandbox is always on: the office never starts it with `--no-sandbox`. Two things have to be in place, and neither stops the office from starting. If one is missing, the board says renders are unavailable and why.

- **The browser** (about 100 MB to download, 200 MB on disk) goes into one folder every install and launch shares: `~/Library/Caches/droid-office/browsers` on macOS, `$XDG_CACHE_HOME/droid-office/browsers` (default `~/.cache/droid-office/browsers`) on Linux, and `%LOCALAPPDATA%\droid-office\browsers` on Windows. `DROID_OFFICE_BROWSERS_PATH` moves it. It needs no admin rights. The Mac app downloads it in the background at launch and again after an update that pins a new revision (`~/Library/Logs/Droid Office/browser.log`). Developer checkouts can run `droid-office browser install` to download it by hand and `droid-office browser status` to check whether it's there. The office also downloads it on first use; a failed download leaves the office running and reports why renders are unavailable.
- **On Linux developer checkouts, its system libraries** need admin rights. As an admin, run `sudo node <checkout>/node_modules/playwright-core/cli.js install-deps chromium` (the error the board shows names the exact command for your checkout). `deploy/provision.sh` does this on the AWS box. Playwright has library lists for Ubuntu 22.04 and 24.04 and Debian 12 and 13, on x64 and arm64. macOS (Intel and Apple Silicon) and Windows 10 and 11 on x64 need nothing more. These source platforms are not production install targets.
- **On Ubuntu 23.10 and later**, AppArmor stops unprivileged programs from using the user namespaces Chromium's sandbox needs, and it fails with *No usable sandbox*. With admin rights, `droid-office browser apparmor-profile | sudo tee /etc/apparmor.d/droid-office-chromium` followed by `sudo apparmor_parser -r /etc/apparmor.d/droid-office-chromium` installs a profile for that browser alone. `deploy/provision.sh` installs it on the AWS box.

### The Mac app

On a Mac with an Apple M-series Pro, Max or Ultra chip running macOS 14 or later, **Droid Office.app** does all of this for you: it starts the office, opens it full screen, and updates itself. Download `Droid-Office-<version>-arm64.dmg` from the [latest release](https://github.com/nikships/droid-office/releases/latest), open it and drag **Droid Office** into Applications. It's signed with a Developer ID and notarized by Apple, so it opens without a warning. It needs no Node.js of its own (the office runs on the app's built-in Node), but it does need `git` and, for the GitHub boards, `gh` signed in (`gh auth login`). It installs and signs in `droid` itself, in [the welcome](#the-welcome).

- **Requirements, checked at every launch.** macOS 14 or later (the build's `LSMinimumSystemVersion` is 14.0, so Finder refuses an older Mac, and the app checks again itself), Apple silicon (the release is arm64 only) and an Apple M-series Pro, Max or Ultra chip, read from `sysctl machdep.cpu.brand_string` (`src/desktop/requirements.ts`). On a base M chip, an Intel Mac or a chip the app can't identify, it shows a message that names the chip and quits. Nothing falls back to a lesser mode. The same goes if the native presenter fails to load or Electron never delivers a shared GPU texture: an error dialog, a line in `~/Library/Logs/Droid Office/startup.log`, then quit. The updater won't offer a release to a Mac older than macOS 14 (`minimumSystemVersion: 23.0.0`, the Darwin version, in `latest-mac.yml`). `DROID_OFFICE_ALLOW_ANY_CHIP=1` skips only the chip check, for CI's base-chip virtual machines; it is not a setting for a Mac you use. `Droid Office --startup-check --user-data-dir=<folder>` runs these checks without a window and exits 0 or 1, which is how CI tests the packaged app.
- **How it draws.** The office page runs in a hidden offscreen Chromium window (`offscreen.useSharedTexture`, `sandbox: true`, `contextIsolation: true`) and never presents itself. Electron hands every painted frame over as a GPU shared texture (an `IOSurface` on macOS), and a native Metal presenter (`native/presenter`, a Node-API addon loaded only in the app's main process, never in the page) shows it in a `CAMetalLayer` view inside the visible window, with no CPU copy. A new frame replaces a frame that was still waiting, so there is no queue of stale frames. The addon draws the newest frame on the GPU and presents it with `CAMetalLayer` and `displaySyncEnabled`, which puts it on the display's next refresh. Chromium's frame clock, set to the display's refresh rate and the FPS limit, decides when frames arrive; the addon does not run a display link by default (`CAMetalDisplayLink` shows each frame about five refreshes, 40 ms at 120 Hz, after its update in a window, which Apple documents as higher latency in windowed modes). At the 40 and 60 FPS limits on a 120 Hz display a frame therefore shows at the refresh after it arrives, and Chromium's own jitter shows up as about one frame in six seconds shown a refresh early and one a refresh late; holding frames to the refresh grid (`paced`) removes that but costs about 15 to 20 ms of latency in a window, because the compositor needs longer to show a frame handed over for a later time than one presented at once, so it is not the default. `DROID_OFFICE_PRESENT_MODE=paced|link` picks held-to-the-grid or display-link presentation for diagnosis only, and `office.presenterStats()` reports the mode in use. The addon returns each texture to Electron only after the GPU has finished reading it (Electron's pool is about ten textures; the presenter holds at most a few). The offscreen page is asked for the display's own refresh rate (120 Hz on ProMotion), so the page's 40, 60 or 120 FPS limit (`render-pace.ts`) still paces against the refresh the player has. Chromium drops an offscreen page to 60 frames a second about 120 ms after any input event reaches it (a mouse move or a key, sent by the app or through the DevTools Protocol; `getFrameRate()` still reports the old rate) and keeps it there until the frame rate is set again. Under a steady stream the drops keep landing, and the rate holds only when it is set again several times per frame (a set every 8 ms or slower lost it in testing), so from the first input event until 300 ms after the last the presenter sets the rate every 3 ms (`InputFrameRate` in `src/desktop/presenter-model.ts`), never while idle or hidden. Measured on a 120 Hz display this keeps the page at 120 frames a second in every 250 ms bin of a 4 s stream of mouse moves (125 and 1000 Hz, sent and through DevTools) and of keys, against 60 without it, for about 3 to 5 points of the main process's CPU while input flows. On a display that can show brighter than white the page renders float16 (`rgbaf16`) and the layer is `RGBA16Float` in extended linear sRGB, so the HDR output of **Settings → Display** reaches the display; the layer asks for EDR headroom only while the page's HDR is on. Elsewhere the page renders 8-bit sRGB. The page is created at the sharpest connected display's scale factor and is not rebuilt if a display with a larger scale is connected later; relaunch the app for that. A minimized or covered window stops painting, drops the offscreen page to 1 FPS and tells the office page it is hidden (Electron's offscreen mode does not change `visibilityState` by itself), so the office's idle and hidden render pause applies. `<select>` lists do not paint in Electron's offscreen mode, so the page draws its own. `office.presenterStats()` reports what the presenter measured (see the automation API). The addon also exposes `capture()` (reads back a presented frame, used for the tear check) and `setDisplaySync()`, and the `paced` and `link` modes exist beside `direct`; all of these are diagnostics for measurement and tests, not settings. The window is shown only once the GPU has drawn a first frame, so a texture the addon cannot import ends in the startup failure dialog instead of a black window. If the page's render process dies it is reloaded once, and a second crash within a minute asks whether to reload or quit; if the GPU process dies and the page stays silent for 3 s it is reloaded, and if it stays silent again the app says so and quits. About one launch in ten, Electron's offscreen view delivers no frame after the page navigates from the splash to the office (the page runs at full rate and the window stays on the splash); if no frame reaches the window within 1 s of the office page loading, the app restarts the page's painting, again at 2 s, reloads it at 3.5 s, and if it is still silent says so and quits about 3.5 s after that reload loads (about 9 to 10 s in all). Windows the page opens (`window.open`, `target=_blank`) open in the browser and never as Electron windows, because a child of the offscreen page would inherit its shared-texture rendering with nothing to show it.
- **Mouse, keyboard and menus.** The offscreen page has no native view, so the presenter's own `NSView` (`native/presenter/src/input_view.mm`) is the window's first responder and turns what AppKit delivers (mouse, scroll wheel, keys, modifier changes, the input method, focus) into small plain messages for the main process (`src/desktop/presenter-input.ts`). The main process sends them to the page as real input: `webContents.sendInputEvent` for mouse and wheel, the DevTools Protocol's `Input.dispatchKeyEvent` for keys (so `key`, `code` and Cocoa's editing commands arrive as in a browser), and `Input.imeSetComposition` / `Input.insertText` for the input method. A key the input method handles reaches the page as `Process` (keyCode 229), as in a browser. The input method is used only while a text field has focus, so the keys that move you around never wait for it. The cursor shape follows what the page asks for (`cursor-changed`). The Edit menu and the right-click menu act on the offscreen page (`src/desktop/edit-menu.ts`), so Copy, Paste, Undo and Select All work in the office's text fields and terminals.
- **Pointer lock in the app.** Chromium refuses `requestPointerLock()` in an offscreen page (it answers `WrongDocumentError`), so a small script the app injects into the page (`src/desktop/page/shim.ts`, built to `dist/desktop/page/shim.js`) replaces `Element.prototype.requestPointerLock`, `document.exitPointerLock` and `document.pointerLockElement`, and the main process decides by the rules a browser applies (`src/desktop/input-lock.ts`, tested in `tests/input-events.test.ts`): a request needs a click or key behind it, except right after the page let go of the mouse itself; Esc releases the mouse on key down and a request is refused while it is held; Esc coming up releases it too, unless the page took the key with `preventDefault`; losing focus releases it. A request with `{ unadjustedMovement: true }` is refused with `NotSupportedError` when no mouse that reports raw motion is attached, so `player.ts` retries without it, as it does in a browser. The page gets back `pointerlockchange`, `pointerlockerror` and the promise a browser returns. When the lock is granted, the native view hides the cursor and freezes it in place (`CGAssociateMouseAndMouseCursorPosition`) and reports relative motion: from the mouse itself (`GCMouse`, no pointer acceleration) when raw was asked for, else from the events AppKit delivers. The main process sends each as a mouse move at a fixed position with an advancing screen position, which Chromium reports as the exact `movementX` / `movementY`. The clicks that take the mouse back, the settling after one, and the warp rule in `player.ts` need nothing special: the page sees the events a browser would send.
- **What the page can ask of the app.** Nothing but that. The page is not trusted, and its one channel to the main process is a DevTools Protocol binding (`__droidOfficeHost`, `Runtime.addBinding`) that accepts four messages: `lock`, `exit`, `escUp` and `editable` (the caret's rectangle). Each is a JSON string of at most 512 bytes whose shape is checked (`src/desktop/input-bridge.ts`), and is read only from the office's own main frame, in the page's own world, at the office's origin: not a subframe, an extension or another origin. Anything else is dropped. The injected script deletes the binding from the page's globals after it has taken a private reference, so the office's own code can't reach it. Nothing of the native module or Electron is exposed to the page, which keeps `sandbox: true` and `contextIsolation: true`. The shim also draws `<select>` lists and `title` tooltips in the page, since Chromium's native ones don't paint offscreen.
- **Choosing files in the app.** A file chooser Chromium opened for the offscreen page would be a sheet on a window that is never on screen, so the app intercepts it (`Page.setInterceptFileChooserDialog`) and shows the Finder's open panel on the visible window instead (`src/desktop/presenter-input.ts`, with the pure checks in `src/desktop/file-chooser.ts`). Only a file input in the office's own main frame, at the office's origin, gets a panel. The panel filters by the input's `accept` list, checked first (known MIME types and plain name endings only; anything else shows all files), and always offers **All files** too. What the owner picks goes to that input (`DOM.setFileInputFiles`); a cancelled panel changes nothing.
- **The first launch** asks where your office lives: `~/droid-office` (what `droid-office` opens with no folder), or a folder you pick. Pick a folder an office already ran in to carry on with its floors and workers. **Office → Change Office Folder…** switches later. The app remembers the choice in `~/Library/Application Support/com.nikships.droid-office/settings.json`, which can also set `"port"` (default 4600).
- **Starting.** The app starts the office with `droid-office --home <folder>`, or `droid-office <folder>` for a checkout an office was started in as a project, on port 4600, and shows it once it answers. If an office already answers on that port (a `droid-office` in a terminal, say), the app opens that one instead of starting a second. If something else holds the port, it takes the next free one. The office and its workers get your login shell's environment, as they would from a terminal, rather than the bare one macOS gives apps: its `PATH`, and everything else your shell profile exports (`JAVA_HOME`, API keys, `LANG`…). Without a locale from anywhere, they get `LANG=en_US.UTF-8`.
- **Opened from the disk image or Downloads**, the app offers to move itself into Applications. macOS runs it from a read-only copy there, so it can't update itself, and workers' terminals stop working once the disk image is ejected.
- **Full screen.** The window opens full screen. **Ctrl+Cmd+F** (or **View → Toggle Full Screen**) leaves it and goes back. Links to issues, pull requests and docs open in your browser. The app has one window, in one of two modes: the 3D office or the web companion (a plain, resizable window). **Office → Switch to Office Companion** (or **Switch to 3D Office**) changes it, and the app remembers the mode for next launch. A browser on this Mac can still open the companion while the 3D office is open.
- **The menu bar icon.** While the app runs, the Droid Office glyph sits in the menu bar: orange while the office is running, dimmed while it is stopped or starting. **Cmd+Q** (**Droid Office → Close to Menu Bar**), **Cmd+W** and the close button close the window. The Dock icon hides once no window remains: the office keeps running, workers keep working, and paired phones and browsers stay connected. The first Cmd+Q says so once. The icon's menu says how many workers are working or need input and how many phones and browsers are connected, and has a **Notifications** toggle: unless the 3D office is open, a worker that starts to wait gets a macOS notification that opens its terminal too. The icon shows the count of waiting workers beside it, and the Dock icon badges it. The menu also has **Open 3D Office** (or **Open Office Companion**, whichever mode the app is in; with the window already open it focuses it), a single **Switch to Office Companion** / **Switch to 3D Office** item that replaces the window with the other mode's, **Restart Office** (**Start Office** once it has stopped), **Check for Updates…**, **Quit Droid Office** and **Quit and Stop Workers…**.
- **Quitting** (**Quit Droid Office** in the icon's menu, **Droid Office → Quit Droid Office** or Option+Cmd+Q in the window, the Dock's **Quit**, logging out, shutting down or installing an update) works like restarting the office: workers keep running in their terminal host, and opening the app again within 30 minutes picks them back up. **Quit and Stop Workers…** asks first, then ends the workers' terminals with the office. An office the app didn't start (one already running on its port) keeps running when the app quits. The office's output goes to `~/Library/Logs/Droid Office/office.log` (**Office → Show Office Log**). Once the window is up, the app writes what Electron says it draws with (`app.getGPUInfo('complete')` and `app.getGPUFeatureStatus()`: the GPU, ANGLE's backend such as Metal, Skia's backend, and each GPU feature's status) to `gpu.log` beside it; **Office → Show GPU Report** writes it again and shows it.
- **Measuring a packaged build.** `--user-data-dir=<folder>` runs the app with its own `userData` and logs in that folder, apart from the installed app. A run like that shows only an office that is already running on the `port` in `<folder>/settings.json` (never 4600): it starts no office, asks nothing about moving into Applications and does not check for updates. `tools/frame-bench` uses it to run the packaged app beside the installed one against a clone of the office. Without the switch nothing changes.
- **Updates.** Every release on `main` comes with the app (see [Releases](development.md#releases)). The app checks for a newer one at launch and every 30 minutes. When there is one, a single **Software Update** sheet opens on the office window: **Install and Restart** downloads it with a progress bar right there (**Cancel** or Esc stops the download), then the app restarts into it. Restarting keeps your workers running. **Later** closes the sheet without downloading anything, and the background checks don't offer that version again until the next launch. **Droid Office → Check for Updates…** checks now and opens the same sheet, which says so when you're up to date or the check failed (with **Try Again**). It reads the public releases of `nikships/droid-office`, so it needs no GitHub login. What it did is in `~/Library/Logs/Droid Office/updates.log`.

### The welcome

An office whose Droid isn't installed or signed in opens the welcome by itself once the office has loaded, in the Mac app and in a browser alike. It has four steps down its side, each ticked once done, and every step also ticks when you finish it somewhere else (in another tab, in a terminal, or in DroidProxy's own window):

1. **Droid.** **Install** downloads the newest Droid from `downloads.factory.ai`, checks its SHA-256 and, on macOS, that it is signed by Factory, and puts it in `~/.local/bin/droid`, where Factory's own installer puts it. Where the office can't install it (Windows, another `--agent` command), the step shows the command to run instead and **Check again**.
2. **Factory account.** **Sign in** runs Droid's own sign-in and shows its code. **Open sign-in page** opens Factory's page with the code filled in, where you sign in or create an account. The step reads *Signed in as …* when Droid has the account.
3. **Subscriptions** (Macs only). **Connect** Claude or ChatGPT, or another provider under **More**. The office installs DroidProxy if it has to, starts it in the background, and opens the provider's sign-in in your browser (or shows a device code). Once an account is connected, its models go into Droid and the step shows how much of each usage window is left. **Skip** leaves workers on Factory's own models; ⚙️ Settings → **Connections** connects one later.
4. **Ready.** Pick the model new workers start on (the best one that can run is already picked) and **Start**. It becomes the office's Default worker (⚙️ Settings → **Workers**).

Until you press **Start**, or close it once Droid is signed in, it opens again at its next step whenever the office loads, so a reload or a restart halfway through doesn't lose the last steps. An office that already worked never sees it. The ☰ menu opens it again at any time. ⚙️ Settings → **Workers** → **Droid** shows the version, updates it, and signs it in again.

### Open the running office in a browser app window

In Chrome or Edge, open an already-running office and choose **Install** in the address bar, or **⋮ → Cast, save and share → Install page as app**. This only creates a browser window shortcut, not a Droid Office installation. The Mac app (or a developer checkout) still needs to be running. The shortcut has no offline mode and needs HTTPS with a certificate your browser trusts, or `localhost` (including an SSH tunnel).

### Access

There are no office passwords, accounts, sessions or login pages. Each start mints a random LAN token, kept in memory and never written to disk; starting the office prints the join URL and a QR code of it in the terminal. Requests from the office's own machine (loopback) connect freely with no token. Every other HTTP request and WebSocket connection must carry the token as `?t=<token>`; a missing or wrong token is refused.

To connect another browser on your network, use the printed link or scan the terminal's QR code: that is the join URL, token included. The token changes on every start, so after a restart, scan the new code. To keep the office to this machine only, start with `--host 127.0.0.1`: there is then no join URL at all.

A paired phone (see [Droid Office for Android](android.md)) carries a **device token** instead. It opens the office the way the LAN token does, for every page, API and the WebSocket, but it keeps working across restarts until you forget the phone. The phone sends it as `Authorization: Bearer <token>` (or `?d=<token>`). The office keeps only its SHA-256, in its own `.droid-office/devices.json`. A device token that was forgotten is refused everywhere, even on loopback, so the phone knows to pair again.

An office that ran before this had a shared password and per-person accounts. Those are gone: the old `accounts.json` is left unread on disk (in the office's `.droid-office/`, next to `config.json`), and so is the old `chat.jsonl`. Delete them yourself if you want them gone; the office never reads, writes or serves them.

```
droid-office [dir] [options]

      --home <dir>        Where the office keeps its data without a [dir] (default ~/droid-office)
      --projects <dir>    Where the office looks for existing git checkouts to add as floors (default a
                          code folder in your home folder, else the home folder; also settable from ⚙️ Settings → **Office & floors**)
  -p, --port <n>          Port (default 4600, env PORT)
  -H, --host <addr>       Bind address (default 0.0.0.0; 127.0.0.1 keeps the office on this machine)
      --agent <cmd>       The Droid command (default "droid", env DROID_OFFICE_AGENT)
      --agent-args <str>  Extra args for Droid, e.g. "--auto medium"
      --tls-cert <file>   Serve HTTPS with this cert…
      --tls-key <file>    …and key
      --self-signed       Serve HTTPS with a generated self-signed cert
      --trust-proxy       Trust X-Forwarded-* (behind Caddy/nginx)
      --max-workers <n>   Run at most n workers at once, across every floor (env DROID_OFFICE_MAX_WORKERS)
      --city <name>       Put the office in a real city: its sun and live weather (open-meteo.com)
      --weather <kind>    Pin the weather: clear, cloudy, rain, storm, snow or fog

droid-office setup [--projects <dir>] [--project <dir>]... [--home <dir>]

  The first-start walkthrough again: the workspace folder, and which of the
  git checkouts in it are floors. With --projects / --project it asks nothing.
  Run it while the office is stopped.

droid-office prune [dir] [-n|--dry-run] [-f|--force]

  Removes leftover worker worktrees under .droid-office/worktrees/ and their
  office/* branches, in one floor's checkout (dir). Anything with uncommitted changes or unpushed commits is
  kept unless --force is given. A worker across several projects has worktrees of them in its
  own floor's workspace: prune each project to clear those out.
```
