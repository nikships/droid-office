# How it works

```
browser ──HTTPS/WSS──▶ droid-office (Node)
                         ├─ node-pty ─▶ droid (one PTY per worker)
                         │    └─ headless xterm mirror ─▶ laptop screen frames + late-join snapshots
                         ├─ loopback-only hook server ◀── Droid hooks (per-worker token)
                         ├─ gh issue/pr list (cached, refreshed every 90s)
                         ├─ ps + lsof every 4s ─▶ guests: agents run by hand in a floor's checkout
                         ├─ Whiteboard store per floor ◀── office-whiteboard (hook token)
                         │    └─ headless Chromium (playwright-core) ─▶ card PNGs, thumbnails, the wall
                         └─ /api/image ─▶ fetches pictures for the walls (cached)
```

- **Worker state at shutdown.** `WorkerManager.shutdown()` saves its final `workers.json` snapshot once. Repeating shutdown does nothing, and late task-naming or terminal callbacks from a stopped manager cannot overwrite the next manager's saved state. Departed workers stay removed, and newly formed teams survive a restart.

- **Android worker views.** `core/Asks.kt` checks whether a local Droid worker is in `needs_input` with a readable numbered menu. `WorkerScreen.kt` opens in Thread only for that answerable question while connected, and otherwise opens in Raw TTY. It waits for the first screen before keeping the default, so a screen arriving after the worker still gets considered. A draft answer forces Raw TTY, and later screen or status updates never override a chosen view. Raw TTY's **Direct** toggle hides the composer without discarding its draft or attachments and gives the terminal a native Android input connection (`TerminalKeyboard.kt`). Characters, composing-word revisions, deletes, Enter and hardware keys go immediately through `term.input`; `core/DirectInput.kt` replaces only a revised composition's changed suffix. Leaving Direct mode, losing focus or disconnecting drops the input connection so stale keyboard callbacks cannot type later. The bundled xterm page stays read-only and never forwards its query replies.

- **Floor HUD and branch.** The top-left floor name shows the floor's worker base, defaulting to the repository's default branch (`origin/HEAD`, else `main` or `master`). Click it and choose **Floor branch → Switch branch** to use an existing local or origin branch, or choose **Repository default** to clear the override. The server switches the shared checkout with the same no-data-loss and occupancy guards as a fresh hire; a refusal is shown in the menu and leaves the saved choice unchanged. The override lives in that floor's `.droid-office/floor-branch.json` and survives restarts. It takes priority over *Where fresh workers start* for new hires and each repository in a workspace. Existing worktrees and subagents' explicit/lead bases stay unchanged. Automatic return after a merged PR uses this base too and never moves away from the selected branch just because it merged. Worker system prompts name the floor branch and ask workers to reread the setting before new tasks and checkout cleanup; saved custom prompts receive the policy when an override is set (an empty prompt remains empty). Branch names keep their case and ellipsize with the full name on hover; the tooltip also shows the actual checkout branch when it differs. Non-git floors, the lobby and roof have no branch controls.

- **Terminal shortcuts.** Command+Left/Right cycles this floor’s running local agent and shell terminals in desk order (including bean bags and board kiosks), followed by the boss monitor’s shell, wrapping at either end. `terminal-cycle.ts` filters out stopped workers, lost worktrees, guests (information-only windows) and cloud sessions (which have no local terminal). It uses only the current floor’s worker slice, never travels or resumes a process, and recalculates the order on each press so departures and status changes are reflected. From the office it opens the first/last terminal; inside the front terminal it captures the keys before xterm or browser history, but text fields and other dialogs keep native Command+arrow behavior. Held keys do not skip through terminals; the shortcut is inactive on the roof or during travel, climbing or picture hanging.

- **Floor shortcuts.** Command+1–9 switches directly to that numbered floor in the floor menu; Command+0 is floor 10. The roof is not numbered or included. `floor-shortcuts.ts` captures these keys before terminals, emotes and browser tab navigation, including inside windows. `switchFloor` sends `floor.go` immediately, with no fade, elevator animation or artificial delay, preserving position and view (standing up first if seated). Arrival applies the requested position, including the street-height adjustment between floors. A held key, the current floor or a trip already in progress does not start another switch. `office.teleport(floor)` uses the same path for automation.

- **Player height.** `player.ts` keeps eye height between 1.4 and 4.2 meters above the feet, smoothly easing toward a target changed by holding Up/Down. Feet, walking collisions and jump physics stay unchanged. Height controls also work while seated or on the ladder, without standing up or climbing; windows and text fields keep their own arrow-key handling. The render loop stays at full speed while height changes, and aiming and sound use the actual camera position. Height starts at normal on each page load; `office.height(scale)` uses the same easing for automation.

- **Returning to the game.** Closing the last window recaptures the mouse. After a click (Send home, Cancel, ✕ or the backdrop), `player.ts` ignores the first nonzero captured movement, which can contain the browser's cursor warp even if you wait before moving. Zero-delta events do not use up that guard; deferred lock requests retain it. The hand's follow-through is held for at most 150 ms, or until it rests for 100 ms. Keyboard closes and ordinary scene-click capture look immediately. Captured movement is otherwise used whole, however fast: only in the first 250 ms after a lock lands is a single move of more than 250 px in either direction dropped, as the cursor warping to the middle of the page. **Raw mouse input** (⚙️ Settings → Graphics → Mouse, off by default) asks for the lock with `unadjustedMovement: true`, so the view follows the mouse's own counts without macOS pointer acceleration. Where the browser answers that it can't (`NotSupportedError`), the office asks again for an ordinary lock and stops asking for raw input for that page; a change applies the next time the mouse is captured. **Look sensitivity** (the same Mouse group, 0.1× to 3×, 1× by default) multiplies how far captured movement turns the view, in the browser and in the Mac app, raw input on or off, and applies at once; dragging to look without the lock keeps its own speed.

- **Android app updates.** The app's `UpdateController` checks the public GitHub latest-release API on foreground entry, at most hourly per running process (15 minutes after failures), or immediately on a manual check. Android's version comes from the APK filename: Mac-only releases carry the existing APK and its version unchanged, so they do not prompt for an Android update. Its final version number is the commit count when that APK was built. `update/GitHubUpdates.kt` uses a separate unauthenticated HTTPS client with HTTP cache validators; downloads start only on **Update now**, stream to private cache and are checked against GitHub's SHA-256 digest and the installed package/signing key before a narrow, read-only `FileProvider` URI opens Android's installer. Failed checks don't block the office, finished APKs are reverified and reused, and the latest-release webpage is always offered as the fallback when a newer version is known. See [android/docs/updates.md](../../android/docs/updates.md).
- **Status.** Droid workers start with a `--settings .droid-office/droid-hooks.json` overlay: hooks (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `Stop`) post to `/hooks/droid`, a server bound to `127.0.0.1` and authenticated by a random per-worker token. The hooks use `curl` when it's there and fall back to a small Node helper when it isn't; they merge for that process only and never edit your Factory settings. Right after the overlay comes `--append-system-prompt-file .droid-office/system-<worker id>.md`: the `worker.system` prompt filled in with the worker's name, written again at every launch and resume and removed when the worker goes home. When that prompt is empty, the flag and the file are left out. A worker's first message (its task, a board agent's or subagent's brief, the carry-on after a restart) is not passed on droid's command line, because droid started with a prompt argument never opens `/rewind-conversation` in that run: the office pastes it into the input box when `SessionStart` says droid can take input, or, when no `SessionStart` has come 15 seconds after the start, once the screen shows the `? for help` footer. Until then it is saved in `workers.json` with the terminal, so an office restarted before `SessionStart` (its terminal kept in the host) still types it in, once. A `Notification` with `permission_prompt` or `elicitation_dialog` means *needs input*, and one with `idle_prompt` (what droid sends when a turn is cancelled with Esc) means *done*, as does `Stop`. A `PreToolUse` of `AskUser` (or `AskUserQuestion`, `request_user_input`) also means *needs input*. The prompt is answered when the next tool starts or when the tool it asked about finishes (`PostToolUse`); droid sends nothing in between. A subagent droid starts with the Task tool posts with the worker's token under its own session, announced by a `SessionStart` with `calling_session_id`: its permission prompts and questions count for the worker, while its own start, prompt and `Stop` don't, and the worker keeps (and resumes) its own session. Some turns start with no hook (a message queued with Ctrl+Enter), and hooks that fire while the office is down for longer than they retry are lost, so every second the office (`reconcile` in `src/server/workers.ts`, the patterns in `src/server/droid-screen.ts`) also reads the bottom rows of each agent's terminal: droid's spinner line (`Press ESC to stop`), a permission prompt or AskUser dialog, or the `? for help` footer at rest. A dialog counts only when its key hints (`inspect approval details`, `ESC stop agent`) are below any `? for help` footer, since a dialog takes the footer's place: a reply or the input box quoting them above the footer is at rest. Once the screen has said one thing for 4 seconds with no hook in that time, a status it contradicts follows it: a busy screen that is still printing means *working*, a dialog means *needs input*, and a footer with nothing printed for 4 seconds means *done*.
- **Shells.** Press **B** at an empty desk to open a plain login shell for dev servers, git or tests. It subscribes and streams like any worker's terminal. The boss's monitor is another one (`OfficeShell` in `src/server/office-shell.ts`), with no worker and no desk: it isn't in the worker list or the worker limit, and it runs in the floor's checkout for as long as the floor does. Its screen is a `screen` frame on `office-shell`, like a laptop's. Sitting in the boss's chair and pressing **E** opens it (`shell.attach`, `shell.input`, `shell.resize`), and every window that has it open gets the same stream. `exit` starts another one. `shell.json` remembers the terminal host's session and the size, and `shell.ansi` the scrollback, so an office restart picks it up the way it picks up a worker. Taking the floor off stops it.
- **Guests.** Every 4 seconds one scan for the whole building (`GuestScanner` in `src/server/guests.ts`) lists this user's processes with `ps` (pid, parent, terminal, start time and executable; the command line only for `--resume <id>` and the office's own `--settings …/.droid-office/droid-….json`), keeps the agent CLIs (`droid`, `claude`, `codex`, `opencode`, `grok`, `muse`) that have a terminal, and reads each one's working directory with `lsof -a -p <pids> -d cwd -Fn` (`/proc/<pid>/cwd` on Linux; nothing on Windows). Left out: anything under a `droid-office-ptys` terminal host, the office itself or one of its workers' terminals, anything launched with an office's hook settings (another office's workers too), an agent under another agent (its helpers), and headless `exec` runs. The working directory, symlinks resolved, is matched against the floors in `floors.json`: the floor whose checkout it is, else the innermost floor it's inside (a subfolder, or a worktree under `.droid-office/worktrees/`); the home floor matches only the home folder itself, and a folder that isn't in any floor's checkout shows nowhere. Inside an office worker's own worktree or workspace, the process is listed on that worker (`WorkerInfo.outside`) rather than seated. Each guest is a `WorkerInfo` with `guest` set (pid, tty, provider, cwd, start time and `seen`), sent with the same `worker.update` and `worker.remove` messages as workers but kept by the floor's `Guests`, never the `WorkerManager`: so the worker limit, the team, sending home and the leave-on-merge sweep never see it, and the server refuses every message that acts on a worker (prompt, kill, resume, shoot, PR, changes) for a guest id with a toast saying why. Its id is its pid and start time, so a later process with the same pid is someone new, and `guests.json` in the floor's `.droid-office/` keeps its desk, name and whether its last turn was seen, so it's back where it was after an office restart for as long as its process runs. Hires and subagents treat its seat and name as taken. A droid guest's session is the one in `~/.factory/sessions/<folder>/` it was started to `--resume`, or, when it's the only droid guest without one in that folder, the transcript there written most recently since it started (never an office worker's); with two in one folder nobody can say whose transcript is whose, so neither gets one. Its status is read from the end of that transcript: an `agent_turn_outcome` line ends a turn (*done*, waiting on you until someone opens its window, unless it had finished before the office first saw it), a prompt or a reply since then is *working*, and nothing yet is *ready*; the model comes from the session's `.settings.json`. Without a transcript it is only *running*. Opening its window gets a banner from the server instead of a terminal snapshot, redrawn when the guest changes; the window takes no input. A guest whose process is missing from two scans in a row goes home. Bringing a guest in (`guest.bringIn`, `Floor.bringIn`) is the one time the office touches a process it didn't start, and only when the owner asks. The guest must be droid, working in the floor's checkout itself (an office worker runs there or in a worktree of its own), with a session tied to it, and between turns: `GuestInfo.cantBringIn` says which of these fails, and its transcript is read once more right before, so a turn started since the last scan isn't cut off (a permission prompt reads as mid-turn, so it is refused too). It needs room under the worker limit. Its desk stays held while `stopGuest` checks with `ps` that the pid still has the same start time and sends it SIGTERM; droid saves its session and gives its terminal back to the shell. Once `ps` no longer shows it (within 5 seconds, else the guest stays a guest and the owner is told), the guest leaves and `WorkerManager.takeIn` seats a worker at its desk, with its name and color, in the checkout, running `droid --resume <session>` on the session's own model. Only then: two droids in one session would write over each other. A scan from before it quit doesn't seat it again. `droid-office prune` runs the same discovery and keeps any worktree an agent is running in, even with `--force`.
- **Nearby offices.** After its HTTP or HTTPS server starts, the CLI uses `bonjour-service` to advertise `_droidoffice._tcp.local` over mDNS. The instance name identifies the laptop and port; the SRV record uses the actual listening port and only addresses served by the bind. Wildcard binds advertise LAN adapters, with IPv4 first, and exclude common VPN and container adapters. TXT contains just `v=1` and `scheme=http` or `scheme=https`, never a password, token, project path or worker data. Discovery is best-effort and stays on the local network. SIGINT and SIGTERM unpublish the service and close its multicast socket without changing how workers shut down or survive a restart.
- **Isolated branches.** When you hire with a task, you can tick *own git worktree*. The worker then gets its own `office/<name>` branch under `.droid-office/worktrees/`, so parallel workers never share a checkout. Just before cutting it (a hire or a subagent), the office runs `git fetch --no-tags origin <branch>` (`src/server/worktrees.ts`, 15s, a burst of hires shares one fetch per branch, and a failure is logged once). `<branch>` is the selected floor branch when set, otherwise the default branch (`Worktrees.defaultBranch`: what `refs/remotes/origin/HEAD` points at, else `main` or `master` on origin or here) while *Where fresh workers start* is *Latest floor branch* (`src/server/saved-switch.ts`, the office's `.droid-office/fresh-main.json`, on by default), else the branch the checkout is on (and the checkout's branch when there is no default branch). It branches from `origin/<branch>` when the local `<branch>` is strictly behind it or missing, so pull requests merged since you last pulled are in it. It branches from the local branch instead when that already has all of origin (commits not pushed yet), or when there's no origin or the fetch fails. When both have moved on, it starts from origin and a toast says how many local commits it left out (`starts from origin/main, without the N commits on main that origin doesn't have`). The floor's own checkout is never moved or cloned; the fetch only refreshes the base a worktree is cut from. The office keeps `worktree.branch` on the branch the worktree is actually on: it reads it when the worker comes to rest or its process exits, when the office starts, when the pull-request list arrives, and before **O** or sending the worker home. A branch the worker creates itself (`git checkout -b`), or a rename of the office branch (`git branch -m`, matched only by the reflog line `Branch: renamed refs/heads/…`), is the one that is followed, and `worktree.made` remembers `office/<name>` until that rename. Deleting the office branch is not a rename, so send-home then removes only the worktree and leaves the branch the worker is on. Sending it home deletes the branch the worker made. The office branch is deleted only when it holds nothing that branch lacks, and is kept while it still has commits no remote, the project's checkout, or the current branch has — those commits still count as work after the worker has switched away. A branch that already existed when the worker was hired (its reflog is older, like `main`) is never deleted. `Worktrees.sendHome` makes that choice and does the deleting, for one worktree and for each worktree of a worker across repositories, and says what it deleted and kept and why. Gun dismissal (`Worktrees.dismiss`) does not use it, and `droid-office prune` keeps its own `describeWork` and `--force` check before deleting. When you send that worker home you choose whether to keep the worktree and branch, delete the worktree, or delete both, and the office warns you first about uncommitted changes or commits no remote has. Those commits include what the worktree's own `HEAD` holds while it is detached (`git checkout --detach`, a rebase), which no branch may have, so sending it home with no choice keeps the worktree. `droid-office prune` clears out whatever was kept, once it is safe, and treats `worktree.made` as that worker's branch too. With *Workers whose pull request merged* set to go home by themselves (`src/server/leave-on-merge.ts`, saved in `.droid-office/leave-on-merge.json`), each floor looks again whenever the PR list comes back or a worker changes, and uses the same call as the purple bubble (`workerPr` in `src/shared/status.ts`). A worker goes with the office's usual check for work its worktree would lose, except that commits up to the merged PR's head (GitHub's `headRefOid`, GitLab's `diffHeadSha`) count as delivered, even once the forge has deleted the branch.
- **Fresh workers and the checkout.** With *Latest floor branch* on, a fresh agent hired without a worktree at a desk (by you or the boards; not a subagent, not a board agent, not a shell) waits for `git fetch origin <floor branch (the repository default when not overridden)>` like a worktree hire, and `WorkerManager.spawn` calls `Worktrees.freshen` before its terminal starts. That does nothing when the checkout is on the default branch and has all of `origin/<floor>`. Otherwise it leaves the checkout alone and toasts why when someone else is in it (another office worker without a worktree whose terminal is running, the Team lead included but not the issues, PR or Pipeline agents, and any guest on the floor; a guest or a worker mid-turn blocks any move, while a worker at rest only blocks leaving the branch it is on, so a checkout on a stale `main` is still fast-forwarded), when a merge, rebase, cherry-pick, revert or bisect is under way, when HEAD is detached, or when tracked files have uncommitted changes on another branch. From another branch it then runs one `git switch`: `-C <floor> origin/<floor>` when the local branch is behind origin's (or `--create … --track` when there's no local one), so a refusal leaves everything as it was, else plain `git switch <floor>`. On the default branch and behind, it runs `git merge --ff-only origin/<floor>`. Every switch and merge passes `--no-overwrite-ignore`, so an ignored local file is protected too if the destination starts tracking it. A default branch with commits origin lacks is switched to but not moved, with a toast. The floor's `project.branch`, which the Changes window of a worker in the checkout diffs against, follows the switch. Nothing stashes, resets or deletes. The same `freshen` runs without a hire, from `WorkerManager.settleCheckout`, whenever a floor's pull request list arrives and *Latest floor branch* is on: when the checkout's branch has a merged PR whose `headRefOid` is the commit the checkout is on (`Worktrees.delivered`, so a squash merge counts and a branch with newer commits doesn't), it fetches and switches back to the floor branch even with workers at rest in it, since nothing on that branch is left to come back to. It stays silent when it has to leave the checkout alone and tries again with the next list, and toasts only when it switched. A subagent's worktree starts from `Worktrees.resolve` of `--from` (a local branch, `origin/<x>`, a branch only on origin, or any commit) or of its lead's `HEAD`, read in the lead's worktree; with no `--from` that commit is moved up to origin's copy of the lead's branch when it is strictly behind it (`Worktrees.caughtUp`), after that branch is refreshed. An explicit origin branch is fetched independently of *Where fresh workers start*, with a refspec that updates its remote-tracking branch even in a single-branch clone; a local branch, tag or commit needs no fetch. `worktree.from` is the branch the Changes window diffs against; it is also the PR target when it exists on origin, otherwise the checkout's pushed branch or the default branch is used.
- **Worktree setup.** `src/server/worktree-setup.ts` and `src/shared/worktree-setup.ts`. Once a worker's worktree is cut (a hire or a subagent), the office works out what it gets from the worktree itself, which is on the branch the work starts from: the floor's own setup from ⚙️ Settings (the floor's `.droid-office/worktree-setup.json`) if it has one, even an empty one; else `worktree.setup` and `worktree.copy` in a committed `.droid-office.json`, plus the patterns in `.worktreeinclude`; else the install the lockfiles at the root call for (one JavaScript package manager at most, then uv, Poetry, Pipenv, Bundler, Composer, Mix) and `/.env`, `/.env.*`. A `.droid-office.json` that isn't valid counts as none, and Settings says why. When there's a command, or any untracked file matches, it writes a plan to `.droid-office/setup/<worker>.json`, and the worker's first terminal runs a login shell with `node .droid-office/worktree-setup.cjs <plan>; exec <agent>` (`&` on cmd.exe), so the agent takes the shell's place and a resume never sets up again. The script (the office's own node, `SETUP_SCRIPT`) deletes the plan, lists the checkout's untracked files with `git ls-files --others --ignored --directory --exclude=<pattern>`, copies each one that isn't in the worktree yet (a clone where the file system can, nothing under `.droid-office/`), then runs the command with the shell in the worktree, with `DROID_OFFICE_ROOT_PATH` and `DROID_OFFICE_WORKTREE_PATH` set. A worker across repositories gets a step per repository, each with its own floor's setup. It posts `WorktreeSetup` to the worker's hook URL when it starts and when it's done: the desk card says *Setting up its worktree*, the 12-second check for a Droid stuck on a login waits until 12 seconds after the setup ends, and a failed command (it always exits 0) toasts and is put ahead of the worker's first message with the last 40 lines it printed. The command's output is piped through the script rather than inherited for that, because Droid clears the terminal when it starts. `worktreeSetup.get` and `worktreeSetup.set` read and change the floor you're on; `worktreeSetup` answers, and goes to everyone on the floor after a change.
- **Pull requests.** **O** at a worktree worker's desk runs `git push -u origin <branch>` in its worktree, then `gh pr create` (or the floor's forge) with the task as the body and the commits listed. `<branch>` is the one the worktree is on now, which may be one the worker made itself rather than `office/<name>`. The base is the branch the worktree was cut from (`worktree.from`: the default branch, the checkout's branch, or for a subagent its lead's branch), if that branch is on the remote, else the branch the checkout is on when it has been pushed, otherwise the forge's default branch. The Changes window uses the same pushed-branch check (`Worktrees.pushedBranch`), with the default branch as its last candidate, so a subagent's unpublished lead is not used as a PR target. Its diff still shows only what it changed relative to its lead. The PR number is saved with the worker, so the board can point back at the desk.
- **Across repositories.** A worker hired with other floors' projects (`WorkerInfo.repos`, `makeWorkspace` in `src/server/workers.ts`) gets a workspace folder, `.droid-office/worktrees/<name>/` on its own floor, with a worktree of its own project and of each other one in it, all on `office/<name>`, named after their checkouts. Each is cut from that checkout's fetched base (the same `git fetch origin <branch>` as a single worktree; the floor's checkout is never cloned or moved), and its `from` branch is what that project's pull request targets. Two checkouts of the same repository are refused, and so are more than 8 other projects. The workspace isn't a repository; the agent starts there with `GIT_CEILING_DIRECTORIES` set to its parent, so git run in it finds nothing instead of the floor's own checkout, and the `worker.repos` prompt is written there as `AGENTS.md`. If one project can't have its worktree, the ones already made are removed again. **O** pushes and opens a pull request in each worktree that has commits and no pull request yet (the issue's `Closes #n` only in the home project's; the others say `Part of owner/repo#n`), then puts a list of all of them between `<!-- agent-office:related -->` markers in each description, replacing the list on later presses. Sending it home runs `Worktrees.sendHome` in each repository, so a deleted office branch, a branch from before the hire and commits only on the office branch are handled there as in one project, and the note names each repository's outcome when they differ. A worker across repositories goes home by itself once no pull request of its is open on any floor's board, one has merged, and none of its worktrees holds work those merges didn't deliver; a failed check keeps the worker. `droid-office prune` leaves a workspace alone while worktrees are in it, and in the other projects lists the worker's branch as checked out elsewhere (and prunes it once that office no longer lists the worker).
- **Changes.** While a desk's Changes window is open, the office runs `git status` and `git diff` in that worker's checkout every two seconds and pushes the file list when it differs. A worker across repositories has a tab per repository, each diffed against that floor's own branch. The diff is against the merge base with the newer of the branch the office was opened on and its origin copy, so it covers the worker's commits and its uncommitted edits, and a pull request merged on the forge that the project never pulled is not shown as the worker's change. Uncommitted edits stay listed even when they undo a change already committed on the branch; their diff and picture preview compare against `HEAD` (or the index) then. Within the list's limit, files with uncommitted edits come first. Commit is `git add -A && git commit`, discard is `git restore` / `git clean` (or `reset --hard` for everything), and Open PR checks the checkout's whole `git status` again and refuses while anything is uncommitted, then pushes the branch and runs `gh pr create`. Open PR and **O** at the desk share `src/server/open-pull.ts`: the same dirty check, open-pull lookup and push, and one base choice, the first of the branch the work was cut from, the branch the office opened the floor on, the checkout's current branch and the default branch that exists on origin. Commit & open PR runs nothing itself: it is a `worker.prompt` with the `changes.ship` prompt filled in from the task card (`WorkerInfo.task`), the tab's branch, its pull-request base and, across repositories, the tab's folder in the workspace; a working agent gets it queued behind what it is doing. Only an agent gets the button, and only on a branch of its own with something to commit or push. **T** attaches the window to the worker's terminal like the terminal window does (`worker.attach`, detached when Changes closes), but never types to it or resizes it: it takes the PTY's size.
- **Terminals.** Each worker's PTY lives in `droid-office-ptys` (`src/server/ptyhost.ts`), a detached process the server starts for each floor and talks to over a Unix socket in that project's `.droid-office/`. On SIGTERM the server leaves the PTYs running there, and the next server takes them back with a snapshot of each screen. Hooks that fire in between retry until it's up. If no server comes back within 30 minutes, the PTYs are ended. The server mirrors each PTY in a headless xterm. Each window that opens the terminal gets a serialized snapshot, then the live stream; closing one window detaches only it. Laptops get compact per-row diffs a few times a second. A terminal wider than a laptop's screen also sends the scrollback rows just above it (`screenHistoryRows` in `src/shared/protocol.ts`, `src/server/screen-frame.ts`), and the laptop takes as many as it needs to fill its height with the text at its normal shape, instead of shrinking the text to the width and leaving black bands above and below. A terminal the laptop already fits, a cleared screen and a program on the alternate screen show only the screen. The PTY takes the size of whichever window typed into it last. Android draws the snapshot and stream in xterm.js inside a WebView, so it keeps the snapshot's scrollback. Its **Phone** view, the one a worker's terminal opens in (a cloud worker's opens in Desktop), sends `term.resize` when selected or when its viewport changes, measured at readable text size; switching it off or leaving the terminal sends back the size from before, unless another window resized it since, in which case the phone switches to Desktop. Its **Desktop** view never sends `term.resize`. The server also remembers, per phone connection, the size each terminal had before that phone's first resize, and when the connection closes it puts back every terminal still at the size the phone last set.
- **Scrollback and search.** Every 15 seconds, for each worker that printed something new, and again as the office shuts down, its last 3,000 lines are serialized, colors included, to `.droid-office/scrollback/<worker>.ansi`. A worker that starts again (after a restart, or when you resume it) gets its old lines replayed into its terminal first, then a dim *office restarted* line. `GET /api/search?q=` matches case-insensitively, treating runs of whitespace as one space, over each worker's terminal buffer. An office from before this release may still have a `chat.jsonl` in its `.droid-office/`; it is left on disk and never read.

- **Sky.** The server decides the weather and tells every window (`src/server/sky.ts`), and every browser renders it as a night sky. Without `--city`, the office sits in the middle of the host's time zone at 40° north (34° south if its clocks go forward in January), and the weather changes every 20 to 50 minutes, with the season's odds. With `--city` (a name, or `lat,lon`), it asks open-meteo.com for the place once and for its current weather every 15 minutes; no key is needed, and nothing but the city's name and coordinates is sent. The office has no roof, so the moon and the sky light the rooms too, but only faintly. - **Screens.** Every in-world display uses an OLED-style material with glossy cover glass (`src/client/world/screen.ts`). A worktree is cut after the same `git fetch` as a hire's, from `--from` (`from` in the request: a branch, tag or commit, no spaces or leading `-`, only with a worktree) or else the lead's `HEAD`, never from the latest main on its own. Four seconds after news, a lead that's done or idle, and that nobody typed into in the last five seconds, gets the `subagent.nudge` prompt with one line per subagent; a busy lead is told once it comes to rest. The Team lead stands at `station-lead`, a kiosk on the east wall that the desks never use, with the `station.lead` brief. The settings (`src/server/subagents.ts`) are the building's, in the office's `.droid-office/subagents.json`. While subagents and the skill are both on, the office writes `~/.factory/skills/droid-office-subagents/SKILL.md` at every start and whenever the settings change, and removes it when either is off. The file carries a line saying the office wrote it: a `SKILL.md` there without that line is the user's own and is never touched. The skill tells droid to use it only when `DROID_OFFICE_WORKER_ID` is set and `office-workers whoami` answers, so it does nothing in droid sessions outside the office, and it sends the agent to `office-workers help` for the commands.
- **Jira.** The office's connection (`src/server/jira.ts`) is one Jira Cloud account for the whole building, kept in the office's `.droid-office/jira.json`; browsers get the site, the email and the account's name, never the token. Connecting runs a small search to check the token, since a `read:jira-work` token isn't allowed to ask who it is. A floor's epic is checked to exist and be an epic, and saved in the floor's `jira-epic.json`. The Jira tab is every direct child of the epic (`parent = KEY ORDER BY Rank ASC`, through `/rest/api/3/search/jql`, up to 500), sorted into *To Do*, *In Progress* and *Done* by Jira's status category. It's read on the same clock as the GitHub boards: every 90 seconds while you're on the floor or a worker is busy, every 10 minutes otherwise, and it waits out the `Retry-After` when Jira rate limits it. Connecting, reconnecting or disconnecting drops the board reads still in flight, so tickets from the old site never come back onto the board, and an issue's details read for the old connection are refused. - **Factory.** The office's connection (`src/server/factory/`, [docs/factory.md](../factory.md)) is one Factory API key for the whole building, kept in the office's `.droid-office/factory.json`; browsers get its fingerprint, whose it is and what it reaches, never the key. Connecting sends one cheap GET per group to `https://api.factory.ai/api/v0`, all at once: `/computers/providers`, `/sessions?limit=1`, `/automations/ci/repository-owners` (which also says whether Factory's GitHub integration is connected), `/wiki`, `/organization/users` and `/service-accounts`. Whose key it is comes from `/computers` (the human owner of its computers) matched against the organization's users, else the only user. The answer goes back once all but the sessions call are in, since `/sessions` can take a minute on a cold call; that group reads *checking* until it lands. A key every group turns down with a 401 is refused. The office checks the saved key again at every start (each group reads *checking* until its own answer lands), and a 401 on any later call marks it rejected and stops every poll. After a key replacement, a poll already running must finish; its old account data is reset before the new account poll, so old credits are not left in the new ledger. An ordinary outage keeps the last good data. Each Factory feature (`src/server/factory/<feature>.ts`) has a slice of one `FactoryState`, which every connection gets in `welcome` and in `factory` messages, a few times a second at most and only when something but a poll's time changed (or a minute has passed, so ages stay right). The registry (`registry.ts`) polls each one only while connected, never twice at once, at its own pace (computers every minute and each managed computer's metrics every 3, sessions every 90 seconds, CI and wiki every 5 minutes), faster while one of your windows or boards shows it (`factory.watch`) or something is in flight, and backs off after errors and 429s. Calls give up after 20 seconds (60 under `/sessions`) and a GET is tried once more. A feature's actions and on-demand reads are its routes under `/api/factory/<feature>/…`, behind the same gate as every `/api/*` route; anything but a GET must come from the office's own page or a paired phone.
- **Droid sessions and credits.** `src/server/factory/sessions.ts` reads the newest 50 sessions every 90 seconds (20 while a session on a Factory computer runs), and the 50 before them every 10 minutes. A session's credits, and a status fresher than the list's, come only from reading it by itself (`GET /sessions/{id}`): the office does that for at most 24 sessions a poll, three at once, the running ones and its own workers' (every floor's, desk and cloud workers and guests alike) first, again when the list says the session changed, every 15 seconds while it runs and every minute while its worker works. - **CI automations.** `src/server/factory/ci.ts` reads Factory's GitHub owners, Droid workflow runs and workflow PRs (`/automations/ci/jobs`) every poll, and the workflow scan only once the scan's own cache (`cacheTtlMs`, 30 minutes) has run out, or on Rescan (`?forceRefresh=true`). - **Droid Computers.** The computers feature (`src/server/factory/computers.ts`, shapes in `src/shared/factory-computers.ts`) reads `GET /computers?includeProvisioningSteps=true` every minute, every 15 seconds while the compute wall is in view, the window is open, or a computer is provisioning or waking. Providers are read every 30 minutes and the computer secrets' names every 5 (the values never come back from Factory). Every 3 minutes, each managed computer's metrics are read from just after the last sample the office has (24 hours back the first time), and the last 6 hours are kept; a BYOM computer has no metrics. A managed computer that sent no sample in 20 minutes is *asleep*. After **Wake** resumes one, it reads *waking* and its metrics are read every minute until a sample comes, an error does, or 12 minutes pass. *This machine* is the computer whose name is the office machine's host name. Its routes (`/api/factory/computers/…`) are `POST` (make one), `POST /bulk`, `GET /repositories` (Factory's GitHub repositories, kept 10 minutes), `GET`/`PATCH /secrets`, and per computer `GET` (the latest, with steps), `GET /metrics?hours=` (1 to 96), `PATCH` (name, remote user), `DELETE` (only with its name as `confirm`), `POST /restart` (`resume` or `reboot`), `/refresh`, `/install-deps` and `/activity`. The wall (`src/client/world/factory-computers.ts`) is two canvases in one bezel, this machine's and the fleet's, each redrawn only when what it shows changes, so the machine's updates don't re-upload the bigger one.

The computers feature reads with `includeUnlisted=true` and keeps the unlisted computers (the ones started for a session) as `instances`, apart from the listed `items` the wall and the window's list show; a new computer can start from an Environment (`source: {kind: 'environment', …}`).
- **Cloud workers.** `src/server/factory/cloud.ts` is the `cloud` Factory feature; each floor keeps its own cloud workers in `src/server/cloud-workers.ts`, apart from the `WorkerManager`, so nothing there (PTYs, hooks, worktrees, the team, the worker limit) ever sees one. Hiring (`POST /api/factory/cloud/hire`) holds the desk, makes the session (`POST /sessions` with the computer, the folder and `sessionSettings`), seats the worker and sends the first prompt as its first message, its pictures inline as base64. `server.ts` hands every `worker.*`, `term.*` and `changes.*` message about a cloud worker to the feature: a prompt is a message to the session, attach and detach mark its window open, a kill interrupts it (and deletes the session when asked), and the rest are refused with a toast. The screen isn't saved; after a restart the first read paints it again. Running or pending is working; idle after a turn the office started, or one it saw run, is done (the same ding, notification and flag a local worker gets). Right after a message Factory can still say idle with the old message count, so a turn counts as over once the session was seen running, a reply made after the message went is listed, or 90 seconds went by. Factory lists a message many seconds after it was made, so a turn that ended before its reply was listed reads the newest messages for up to 90 seconds more, to put the reply at the desk. A 404, or its computer gone from the computers slice or in error, puts it in an error state with the reason. Factory 404s a session it has only just made for a few seconds, so a read 404s without harm until the office has read the session once or it is 3 minutes old, and a message, interrupt or delete for a session made in the last 30 seconds tries again a few times over about ten seconds (`src/server/factory/new-session.ts`, which the Sessions routes use too). Each one's turn is saved with it, so after a restart it's back at its desk and its next read picks the session up by id. A hire on an Environment first starts an unlisted computer from it (`<environment>-<8 hex>`) and reads it every 2 seconds until it's active, 4 minutes at most; the session's folder is the floor's repository's clone there, the first message goes with the `cloud.environment` prompt in front, and a failed hire or sending the worker home deletes that computer.

- **Pipelines.** `src/server/pipelines.ts`, with the shapes and the state words in `src/shared/pipelines.ts`. Each floor keeps a `Pipelines` that reads its runs with `gh api repos/{owner}/{repo}/actions/runs` (the last 30), or with `glab api graphql` (the project's last 30 pipelines) on a GitLab floor, and counts the jobs of up to six live runs for the board's progress bars (`…/runs/<id>/jobs?filter=latest`, or `projects/:id/pipelines/<id>/jobs`). Which GitHub workflows can be started by hand, and their inputs, come from `on: workflow_dispatch: inputs:` in each file, read from the floor's checkout or else from the default branch through the contents API, with a small YAML reader (`parseYaml`), every 5 minutes. **Run workflow** is `gh workflow run <file> --ref <branch> -f <input>=<value>`, re-run is `gh run rerun <id> [--failed]` and cancel `gh run cancel <id>`; on GitLab they're `glab ci run --branch <branch> --variables KEY:value`, `POST projects/:id/pipelines/<id>/retry` (failed jobs) or `POST projects/:id/pipeline` (all of it again, a new pipeline), and `POST …/cancel`. - **Whiteboard.** [docs/whiteboard.md](../whiteboard.md) is the design. One pure reducer (`applyOps` in `src/shared/whiteboard.ts`) applies every change on the server and in the window. Where a mark sits, and the list of what changed, is `src/shared/whiteboard-marks.ts`: the window fits a canvas with 80 pixels of room and the renderer captures one with 48, and each passes its own margin. Each floor's `WhiteboardStore` (`src/server/whiteboard.ts`) keeps the board in the floor's `.droid-office/whiteboard/`: every file a card holds (its HTML, each asset, each picture) is a content-addressed blob in `blobs/<sha256>`, written once, and `board.json` holds the board and an operation record. A commit writes and fsyncs its new blobs, then `board.json` through a temporary file, an fsync and a rename, so a crash leaves the old board or the new one with every file it names. Each window connection and each `office-whiteboard` run gets an epoch and numbers its batches; the record keeps each recent epoch's highest applied number (14 days, 1,000 epochs), so a batch is acknowledged only after its commit and a retry is applied once. A retry from an epoch the record has dropped is refused as expired, never applied again: the window keeps it as a draft. The window (`src/client/whiteboard-sync.ts`) applies its batches at once on its copy, queues them while the connection is down, resyncs on reconnect and sends again what wasn't acknowledged; every committed batch goes to the floor's windows as a patch they replay with the same reducer. Cards hold up to 100 MB of distinct content files and pictures combined, with up to 100 MB per asset or picture, 2 MB for entry HTML and 1 GB of distinct files per floor (binary units). Uploads are buffered in memory and local files are processed synchronously, so larger artifacts can increase peak memory, processing stalls and load times. There is no history. Every independently editable piece (a title, the content, each state leaf, each comment message, each sticky's text, color, box and anchor, and so on) carries the revision and author of its last change, removals leave a small tombstone, and each reader (you, and each worker) has a read point per card: a piece is *changed* for a reader when it's newer than that reader's read point and someone else made it. `office-whiteboard read` moves the read point only for the cards it returned, after it printed everything. Agents reach the board through `/office/whiteboard` on the loopback hook port with their hook token (`src/server/whiteboard-agent.ts`), on their own floor only. `push --file` and `link` collect the local files a page references (markup and CSS, inside its folder, within the limits in `whiteboard.ts`), and `--dir` takes a whole folder. A linked card follows its file through a watcher and a 2-second poll, keeps its last good content and says *Link broken* when the file is gone, and comes back with it. A card's page loads from `/whiteboard/c/<capability>/<path>`, where the capability (an HMAC with the floor's `key`) reaches that one card's files and nothing else, into an `<iframe sandbox>` without `allow-same-origin`, whose `allow` list grants clipboard writes and full screen (which a video's own controls need) and nothing else; `CARD_FRAME` in `src/shared/whiteboard-bridge.ts` is that frame's sandbox, `allow` list and referrer policy, for the window, the server's CSP and the Android page alike. Its answers carry `Content-Security-Policy: sandbox …` with the same flags, so even a card opened directly in a tab runs on an opaque origin, and `Access-Control-Allow-Origin: *` without credentials, which no other office route gets. The office injects its SDK (`src/server/whiteboard-sdk.ts`) at the top of the page: the JavaScript API, form fields into `state.fields`, finding marks' anchors, and the bridge to the window, which accepts a message only from that frame with that load's nonce. The renderer (`src/server/whiteboard-render.ts`) is a headless Chromium driven by `playwright-core` with Chromium's own sandbox on (`src/server/whiteboard-browser.ts`). Each render is a fresh browser context with every permission denied, loading the card the way the window does from a pinned snapshot that keeps its blobs on disk while it runs, at 1280 pixels wide. It waits for fonts, network quiet and the page to stop changing (10 seconds at most), draws the stickies, pictures and comment pins, and captures the full page as 1280×2048 tiles (8 at most) plus a 640×400 thumbnail. Renders are debounced per card and run two at a time; a newer image is never replaced by a slower older one, and a failed render keeps the last good image. The local network is granted to the renderer's own page only so cards can reach machines on it, and the office's own addresses stay blocked. Images are kept in memory, so the office renders every card again when it starts. `read --png` renders the read's own snapshot, or says why it couldn't; without a browser, the board says renders are unavailable and why, and everything else works. Taking a floor off stops its watchers and renders and deletes nothing.
- **Viewport input.** The artifact SDK forwards trackpad wheel/pinch, middle-button drags, temporary Space-pan and navigation shortcuts (including **F** for full screen) over the same frame-and-nonce-bound bridge. Space on a focused button, link, video or audio stays with it, and while something in the page is full screen itself (and for half a second after it gives the screen back) no shortcut, Space or Esc is forwarded. Pointer coordinates are mapped from the frame into the viewport; device deltas stay in screen pixels. - **The picture.** The 3D loop (`src/client/render-loop.ts`, with its pace decided by `src/client/render-pace.ts`, from `src/client/main.ts`) draws every frame, up to the **Frame rate limit** in ⚙️ Settings → Graphics, while the window is visible and something is moving: you, a worker walking, hopping or in the middle of a turn, confetti, the gong, smoke, an elevator ride, rain or snow, and the traffic when you are up on the roof or outside. Once the office has been still for 30 seconds (you standing still, nobody mid-turn, nothing above going), it drops to a few frames a second, so the street outside the windows keeps moving without the laptop drawing sixty times a second. A finished worker holding still beside its card can idle too. Hovering an unlocked cursor does not wake the loop: actually looking, moving or changing the scene does. A hidden tab, or a window fully covered by another window, stops the loop. The connection, worker status and the boards keep running. Both physics and absolute-time poses advance by the same capped simulation step, so neither fast-forwards across the hidden gap; music and shared events keep their own clocks. On macOS the page reports itself hidden once the window is fully covered; being unfocused beside another window does not. A tab opened with `?pace=full` on its address (`http://localhost:4600/?pace=full`) skips all of this and draws every frame (still under the frame rate limit), still, hidden or covered, for screen recordings; other tabs keep the usual pace. The terminal is its own canvas and is not this loop.
- **Graphics.** **⚙️ Settings → Graphics** is kept in this browser. At **Render resolution** 100% with **Temporal anti-aliasing** off, the scene draws straight to the canvas with 4× MSAA. Below 100%, or with TAA on, `src/client/world/upscaler.ts` draws it into a smaller render target first, and three.js writes the same sRGB-encoded colour there as on the canvas, so glass and glows blend the same. With TAA on, each frame is jittered by a Halton (2, 3) sub-pixel offset. A resolve pass filters the samples onto the full-resolution grid and blends them into the last frame's output. That history is reprojected by the camera's motion through the depth buffer and clipped to the colour range around the pixel (TAAU below 100%). Without TAA the image is stretched bilinearly. Either way contrast-adaptive sharpening (**Sharpening**) runs on the way to the screen. The first-person hands draw on top afterwards, at full resolution and outside TAA. The office draws no shadows in either renderer: the shadow map is off and there is no setting for it. **Overhead lights**, 0–100% in 5% steps (100% by default), dims the office's ceiling lights in both renderers: the LED bars, the high-bay lamps, the lights under the loft and the boss office's lamp glow less, and the room's fill light (`skyOffice` in `src/client/world/sky.ts`, the light those fixtures give the room) drops with them. At 0% only the moon, the sky, the laptop screens and the bounce light are left. In Remastered a change bakes the global illumination again, since the probes hold the light the fixtures gave. **Frame rate limit** is 40, 60 or 120 FPS (120 by default), the rates that divide a 120 Hz refresh evenly. It caps the full pace; the idle pace and pausing are unchanged. `gateFrame` in `src/client/render-pace.ts` puts due times on a fixed grid one interval apart and draws the animation frame nearest each one, judged against the display's refresh, which it measures from the gaps between frames. On 120 Hz, 40 is every third refresh and 60 every second, whatever the timestamps' jitter. On 60 Hz, 60 and 120 are both every refresh and 40 alternates one and two. A skipped frame steps and draws nothing, and the next drawn frame's step covers the time since the last drawn one (still capped as a hitch). After a hitch, an idle frame or a pause, the grid starts again from the next frame drawn, so a wake never lets frames through faster than the limit and nothing bursts to catch up. **Performance overlay** (on by default) is the corner readout: frames per second against the limit (`cap 60`), the GPU time of each frame from WebGL's `EXT_disjoint_timer_query_webgl2` (Chrome and the Mac app have it, Safari doesn't) and the share of wall time it keeps the GPU busy, the Mac's whole-GPU **Device Utilization** from `ioreg` (`GET /api/gpu`, only for a page on the office's own Mac, `src/server/gpu-stats.ts`), and the render and output resolution. Its second line is the frame pacing of the last five seconds (`src/client/frame-stats.ts`): the 50th, 95th and 99th percentile time between drawn frames, the frames that missed their slot under the limit, and the refreshes that showed a frame again beyond what the limit plans for (on 60 Hz under 40 FPS the alternating one and two refreshes count as on time). Only frames the full-rate loop draws on an animation frame count; an idle or wake draw starts the count again rather than counting as a miss. With the overlay on, GPU time is timed in two passes, the scene and then the hands with the frame's finish. `office.frameStats()` (see the automation API) returns the same numbers for a whole measurement, with CPU time per pass, GPU time per pass, the measured refresh, the renderer, WebGL's GPU and backend string and whether the mouse is read raw; these are animation-frame timings, a proxy for what reaches the display, not a measurement of it. Apple GPUs clock down under light load, which inflates that utilization percentage, and the timer counts gaps between passes. Compare modes at the same settings, not as absolute numbers.
- **The Remastered renderer.** **⚙️ Settings → Graphics → Renderer** picks **Classic** (the default, everything above) or **Remastered**, live, without a reload. Whether Remastered is on, and whether HDR is on, are kept in this browser (`droid-office.remaster` in localStorage, read back by `normalizeRemaster` in `src/client/remaster-settings.ts`). The picture is fixed: the scene is drawn at 1.0× with 2× MSAA, global illumination at its finest (a probe every 1.4 m with two extra bounces), normal brightness, natural color, subtle light sources, smooth shading and no sharpening. **HDR** is the switch under Renderer, off until it is turned on; highlights then go up to 4× white. There is no quality menu, no resolution slider for this renderer, and no Graphics Lab. `src/client/world/remaster.ts` draws the office at 1.0× into a half-float target with 2× MSAA, then one grade pass applies the locked exposure and tone maps to the display's peak. Sharpening is off, so that pass is skipped. The multisample scene depth is discarded after drawing and never resolved: only color is read by the grade, and the hands clear their own depth. Outside the indoor GI fade, where the probe contribution is exactly zero, the lighting shader skips the seven 3D atlas samples. Axis-aligned faces read a derived six-direction irradiance atlas (`src/client/world/probe-axis.ts`) with one trilinear fetch instead of seven SH fetches and per-pixel SH evaluation. It evaluates the same baked light once when a bake finishes or loads, preserves signed values and padding until after interpolation, and keeps the original sample bias and curved-surface calculation. It is disabled while probes change and disposed with the grid; a uniform, not a new shader variant, switches it on. Static solids reuse only bit-identical position and normal pairs, retaining every triangle and hard edge while reducing vertex storage and repeated vertex shading. Merged batches keep both their own and their source solids' local bounding boxes, so picking skips empty space and hidden subtrees before the same exact triangle hit test. The grade compiles only the selected tone-mapping curve, rather than selecting it per pixel. Painted worktops and metal use a broad, vertex-evaluated room reflection (`src/client/world/surface.ts`), scaled with the overhead lighting and excluded from the diffuse probe bake. A continuous smooth-light ramp, beveled desk and chair edges, and a finer gong silhouette keep surfaces readable up close. A shared, mipmapped single-channel atlas adds static ambient contact under fixed furniture; wall junctions use an analytic fade. These add no render pass or shadow map, and Classic keeps its original light response. Static wall faces are batched by paint, and an identity color grade skips contrast and saturation math. The classic Render resolution, TAA and Sharpening stay on the page and turn grey while Remastered is on; their saved values come back with Classic. The frame rate limit and the overlay still apply. Global illumination is a light-probe grid over the floor (three.js's `LightProbeGridWebGL`) that the office's own lit materials read: it bakes a slice of probes each frame within half of what a frame has (the frame rate limit's interval, or the display's refresh when that is slower: 4.2 ms at 120 FPS on 120 Hz, 8.3 ms at 60 FPS or on 60 Hz, 12.5 ms at 40, never more than 14 ms) of the main thread, so the frame itself still fits its slot while it bakes; a higher limit on a faster display bakes in more, smaller slices. Every floor has the same room, desks and lamps, so the bake hides what shows who is on a floor (each seat's worker, laptop, dance spot and free-seat sign, the bean bags and the team lines) and one bake fits every floor: changing floors or going up to the roof never bakes again. The probes are baked under a clear night's moon and sky, so the weather and lightning never end up in the bake. A finished bake is read back from the GPU and kept in this browser's IndexedDB (`src/client/gi-cache.ts`: the two most recently used bakes, each under its own key, so switching between SDR and HDR loads the other bake back instead of baking it again; a third replaces the one used longest ago). Its key (`bakeKey` in `src/client/remaster-settings.ts`) is the locked picture, HDR, the overhead lights' brightness and the office's version. The next launch with the same key loads it instead of baking. A change to any of them loads the bake saved for the new key, or bakes again when there is none. Each finished bake is saved under its key. There is no button to bake again by hand. While a bake runs, a panel above the bottom of the view (`src/client/warmup.ts`) says **Baking light** with how far through it is and that the frame rate is lower until it's done. The shaders the office, your hands, the wand and its spells, the gun, the roof, the prop models and both renderers can ask for are compiled while the loading screen is up (`src/client/shader-warmup.ts`): the point-light counts a spell or a beam can add, the bounce-light grid on and off, the office canvas at no tone mapping and at the map the renderer is using, and the tone maps your hands can be drawn with. The wand's light stays in the scene, dark, so drawing the wand does not change that count. The browser keeps those compiled shaders, so the next launch does that work from the cache, still during loading rather than when you draw the wand. In either renderer the same panel says **Compiling shaders** for 1.5 s after a frame that added shader programs and took 30 ms or more to draw, which is a material that still showed up after loading; a new material that compiles quickly says nothing. It says it's done for a moment, then fades. **Native HDR** (`src/client/world/hdr-present.ts`) copies the float16 WebGL drawing buffer into an extended-range `rgba16float` WebGPU canvas each frame, so highlights go past white on an EDR display such as the MacBook Pro's XDR panel; where the browser or display can't, Settings → Graphics → HDR says why and the picture stays SDR. A saved Graphics Lab mix is ignored: only whether Remastered is on, and whether HDR is on, are kept.

- **Paired phones.** `src/server/devices.ts` keeps the phones in the office's `.droid-office/devices.json` (id, name, SHA-256 of the device token, `pairedAt`, `lastSeenAt`), written to a temporary file and renamed into place, mode 0600.
