# The Office MCP

Status: implemented. One MCP server, `droid-office`, replaces the three commands the office used to put on every agent's PATH (`office-workers`, `office-whiteboard`, `office-visit`) and the two skills it wrote into `~/.factory/skills` (`droid-office-subagents`, `droid-office-whiteboard`). What those commands' `help` text and the skills taught lives in the server's `instructions` and in each tool's description and parameter descriptions. There is no other interface: the commands, their `/office/workers`, `/office/whiteboard` and `/office/visits` endpoints, the skills and their Settings toggles are deleted. On startup the office removes the old command folder (`.droid-office/bin/team`) from each floor.

## Decisions

- **Building agents.** The Orchestrator and external bots live in [Mission Control](mission-control.md), with no floor or desk. External bots use a separate loopback listener behind Tailscale Serve (Settings → Phone & web → Tailscale MCP), without a local Droid or PTY. Each bot has a revocable key and building-wide teams and inbox. The Orchestrator uses the existing local hook listener with its own terminal hook token, independent of Tailscale; it has no external bot key. Its token lives in the PTY environment and mode-0600 worker state in `.droid-office/orchestrator/.droid-office/`. The reserved `orchestrator` id authenticates only through its own manager, never a floor worker's token.

- **Worker controls for building agents.** An external bot lists a fixed set of tools; the Orchestrator lists the same surface except `office_status`, which the office observes itself. A fixed allowlist gates discovery and direct calls. `office_roster` separates floor workers from Mission Control, including the dormant Orchestrator before its first prompt. Five focused tools in `owner-tools.ts` spawn, prompt, interrupt, answer menus and read threads. Building agents cannot prompt, interrupt, answer or dismiss one another or themselves; only the Orchestrator's terminal and thread may be read. Strict schemas and appropriate annotations remain in `owner-schemas.ts`. Building agents can read floor Whiteboards with `whiteboard_read`, while Whiteboard mutation, visits, raw input, floor-management, general forge, pipeline, settings and connection tools stay internal. Floor workers retain their existing permission-filtered tools.
- **Owner routing and outcomes.** Worker tools resolve ids or unambiguous names across floors; a supplied floor must match. Spawn requires a floor id, name or elevator number. The server generates internal request ids and uses the ordinary owner handler on a virtual connection named after the caller. Results report `done`, refusal, `pending` (no confirmed outcome within 30 seconds) or `unconfirmed`, with notes and a bounded reply. Uncertain mutations are never automatically replayed. Sending home keeps worktrees, branches and cloud sessions by default. Building agents bypass local Subagents permissions and per-lead limits, but obey capacity, model availability and the model allowlist (`SubagentSettings.models` in ⚙️ Settings → Subagents & visits → **Models leads can pick**): `team_models` lists only the allowed models for floor leads, the Orchestrator and external bots alike, and `team_hire` and `office_worker_spawn` (including cloud workers and the resolved default when `model` is omitted) refuse any model outside the allowlist with an error naming the allowed ids. Existing workers keep their saved models when resumed or messaged, and the owner's own hires from a window are never limited. `Team.refuseSpawnModel` applies the rule in `ownerOffice.act`, the one way in for owner-level actions, so a new tool with a model argument gets it too; the rule itself lives in `src/server/model-policy.ts`. Window streaming, subscriptions and heartbeat messages remain internal.
- **Library.** The official TypeScript SDK's server package, [`@modelcontextprotocol/server`](https://github.com/modelcontextprotocol/typescript-sdk) **2.3.1**, pinned, with Zod **4.6.7**. `createMcpHandler` serves stateless Streamable HTTP and builds a low-level `Server` per request for the authenticated caller, so its `tools/list` handler lists only the tools that caller may use and its `tools/call` handler applies the same predicate. Requests whose `Host` is not a loopback name are refused (`hostHeaderValidationResponse`), so a web page cannot reach the server by rebinding its own name. A small adapter (`node-http.ts`) turns the hook server's Node request into a web `Request` and streams the `Response` back. The SDK has no telemetry and discovers nothing on its own.
- **Transport and mount.** Streamable HTTP, mounted on the office's hook server (`127.0.0.1:<hookPort>`) at `/office/mcp`. The tools call the server-side code (`team.ts`, `whiteboard.ts` and `whiteboard-agent.ts`, `visits.ts`) directly, not over HTTP.
- **Identity.** Every protocol request carries `Authorization: Bearer <DROID_OFFICE_HOOK_TOKEN>` and `x-droid-office-worker-id: <DROID_OFFICE_WORKER_ID>`. The token is resolved through `WorkerManager.authenticate`, as the status hooks are. Missing, mismatched, revoked and non-agent identities are refused before protocol initialization; there are no anonymous tools.
- **How Droid connects.** The fallback shipped: one `droid-office` entry in `~/.factory/mcp.json`, with `oauth: false`, the loopback URL, and `${DROID_OFFICE_HOOK_TOKEN}` / `${DROID_OFFICE_WORKER_ID}` / `${DROID_OFFICE_HOOK_URL}` header references. Droid expands variables in headers but not in the URL, so offices on one machine share this entry: whichever office it points at relays a request whose `x-droid-office-url` names another loopback office to that office, so each worker always talks to its own. A live office that already holds a routing entry keeps it (checked with an `OPTIONS` probe); an office takes the entry over at startup and every 30 seconds once the holder stops answering, and removes it only while it points at itself. Runtime `--settings` does **not** load `mcpServers` on tested Droid **1.1.0**. The office merges its entry atomically without clobbering other servers, refuses malformed files or a foreign entry with that name, and removes its own entry when Office MCP is off. Office terminals, shells included, receive the variables for hooks and worktree setup reporting; the server accepts only local agents and refuses shells and cloud workers. A non-office session with those variables unset starts normally and gets no office tools or HTTP connection. The hook listener reuses its port across restarts, and startup refreshes the profile URL when needed. Tests and isolated copies can leave `Config.skillsDir` unset to avoid writing a Factory profile.
- **Hidden tools.** `tools/list` is filtered per caller: a subagent sees no hiring or visit tools, a worker that may not hire sees no team tools, visits off hides the visit tools. A hidden tool that's called anyway is refused with the reason.
- **Waiting.** Leads learn about their team from the office's wake notes. With ⚙️ Settings → Subagents & visits → "Wake the lead" off, and for external workers, which have no wake notes, `team_wait` long-polls: it returns as soon as a watched subagent reports, asks, needs input in its own terminal or settles, at once for matching news the lead hasn't heard (or news after `since`), and otherwise at its timeout (default 30 s, at most 600 s; each call holds at most 90 s on the server so MCP clients never abort with `-32001` request timeouts around 200–240 s, returning `matched: false` with `capped: true` and `cursor` so the caller can continue with `since`). A terminal question counts only once it appears during the wait, and `idle` only once the team settles during it, so a question already waiting or a team already at rest doesn't end every wait at once; open questions are still listed in its response. Its events are read again with the cursor as it answers, so the cursor never passes an event the response leaves out. It listens to each floor's `Team.subscribe` and unsubscribes on return, timeout and when the caller hangs up; a caller may hold four waits at once, and a client that sent a progress token gets progress every 15 s. The stateless transport can't route a later `notifications/cancelled` to the held request, so a cancelled wait ends when its connection closes or it times out. A local lead with wake notes on is not shown `team_wait`: its turn would hold the wake note back.
- **Structured team state.** `team` status keeps its prose for existing callers and adds `structuredContent` fields: `workers` (one compact object per subagent: id, name, floor, desk, `state`, status, task, `taskLabel` provenance/timestamp/staleness, doing, `plan`, `currentTool`/`lastTool`, `lastActivityAt`/`silentForMs`, `queued`, `queuedMessages`, `blockingTool`, `retryingModel`/`modelStatus` cooldowns, model, branch, worktree, PR, `prStatus`/`ci`/`releaseRun` from cached floor state, `lastReportId`/`At`/`Summary`, `openQuestionId`), `news` (typed events with `team:<floor>:<seq>` ids, ISO times and summaries) and `cursor` (one event id per floor). `office_look` and `worker_log` (`src/server/worker-status.ts`) prepend the same structured worker state before terminal text and accept `lines: 0` / `tail: 0` to omit raw terminal output altogether; `office_roster` and `team_status` tag generated worker labels (`generated`, `updatedAt`, and `stale: true` when Worker labels are off) separately from lead/prompt tasks without changing Grok Bot webhook payloads. `verbose: false` makes the text one line per subagent and per event and leaves the whole reports out of `structuredContent`; `team_report_get` reads one in full. `since` returns everything after a cursor, heard or not, and `kinds` only some kinds (`blocked` is `needs_input`), leaving other news unread. A subagent's `state` is `blocked_on_question` while a `team_report` question is unanswered (until its lead messages it or it starts another turn) or an AskUser menu waits in its terminal. Each floor's event seq is saved in `team.json` and never goes back, so a cursor stays valid across restarts.
- **Sibling coordination and steering.** Subagents read `team_board` for same-floor, same-lead task titles, status, branches, declared edit areas, latest notes, the existing structured result's status and 300-character summary (falling back to report prose), without terminal/Git reads or consuming the lead's news. `team_note` posts a short finding and optionally replaces its author's edit areas; `[]` clears them. The latest note and areas survive restart in `team.json`; working siblings that have not reported this turn receive a fenced worker note only through current hook notices. Starting, asking, resting, stopped, already-reported and legacy-hook sessions read the persisted board without queued input or wakeups. Lead status and waits expose edit areas, notes, pending queued messages (`queuedMessages`), and active blocking tool calls (`blockingTool`, such as `gh run watch` or long-running commands). Notes are findings, not assignments or completion reports. With the [noise gate](#inter-agent-noise-gate) on, a note interrupts only the siblings it is relevant to. New hires receive a snapshot capped below 2,600 characters, with single-line clipped notes, outside the literal task fence; the worker card keeps only the lead's original task. `team_message` accepts exactly one of `worker`, `workers` or `all: true`; building-agent broadcasts can span floors. Its default `queue: false` steers busy sessions at the next step (through hook notices when active, or plain Enter in Droid's TUI), `queue: true` explicitly queues behind the turn via Ctrl+Enter, and `urgent: true` cancels a running turn or blocking command via Escape before delivering immediately. `worker_queue` lets leads and building agents inspect (`list`), cancel (`clear`), or pull forward (`promote`, optionally `urgent: true`) pending outbox and TUI-queued messages. Responses distinguish `next_step`, `queued_turn`, `interrupted`, `sent` and `resumed`, include blocking-command warnings when steers wait on a long command, and carry canonical ids, readable names, floors for building teams, and per-recipient errors for broadcasts. Empty teams and entirely failed broadcasts return tool errors; mixed delivery stays successful.
- **Questions.** `questions_list` shows what the owner's phone Asks inbox would for the lead's own subagents: `team_report` questions (with optional `options`) and AskUser menus read from their terminals with the shared `src/shared/asks.ts` parser. `question_answer` sends a team answer as a `team` message, and answers a terminal menu through the same `Answers` queue as the phone, only while the menu's hash in the question id still matches what is on screen. Droid 1.7.1's final **Review your answers** lists the chosen answers and offers option `1`, **Submit answers**; explicitly choosing it sends Enter. The hash includes every review summary line, so edits invalidate the old question id. `office_worker_answer` accepts the same exact menu snapshot with its `review` lines and `choice: 1`. Older CLIs without review still finish normally. Permission prompts are listed but refused: only the person at the desk approves.
- **Non-blocking visits.** `visit_message` returns immediately with its `v-…` id and `delivered` or `queued` status, never waiting for a walk, permission prompt or answer. The normal walking delivery is initially queued: the visitor walks over, speaks and walks home, including for an ask (`walking` → `talking` → `returning`, with no waiting-for-answer pose). A question that cannot go in while the visitor is there remains queued, like a tell. `visit_look` reads a current terminal snapshot directly, without pretending the worker walked somewhere or waiting for an animation.
- **Ask lifetime and replies.** An undelivered ask expires 30 minutes after the visitor sets off; expiry removes its queued question so it cannot deliver late. Delivery starts a fresh **30-minute reply window**, independent of polling, the asker's turn, or the walk home. Only the addressed host may answer, once, with `visit_reply`. The answer is a new normal-priority delivery typed into the asker's session, like a tell: safe queues, permission dialogs and sleeping-worker resume still apply. It does not invent another walk. After expiry, `visit_reply` returns a clear “This ask expired” error and suggests `visit_message` for a tell or new ask. Worker departure, turning Visits off and office restart end open questions; nothing is persisted.
- **Files and images.** Whiteboard paths are resolved against the calling worker's working folder (its worktree or checkout), never the office's cwd. A PNG export comes back as MCP image content.
- **One toggle.** ⚙️ Settings gets one "Office MCP" switch (on by default) in place of the "Subagents skill installed" and "Whiteboard skill installed" toggles. Off: workers get no office tools. On startup the office deletes `~/.factory/skills/droid-office-subagents/SKILL.md` and `~/.factory/skills/droid-office-whiteboard/SKILL.md` only when they carry the office's mark (`SKILL_MARK` / `WHITEBOARD_SKILL_MARK`), and their folders when empty. The Android app has never shown these settings, so it has nothing to follow.
- **Prompts.** The system prompt's "Office tools" section and every notice that used to name a command (team update, lead/visit deliveries, Whiteboard ping, pipeline heal, cloud note) are short pointers to tool names. Detail lives in the server instructions and tool descriptions. Every lead surface (`orchestrator.system`, `worker.system` + `subagent.nudge`, and the MCP `instructions` and descriptions of `team_hire`, `team_status`, `team_wait`, `team_message`, `team_review`, and `team_merge`) codifies the active-manager rule: commit shared prerequisites before hiring, read `team_models` once per batch, parallelize disjoint single-writer hires (with subagents sharing edit areas via `team_board` and `team_note`), inspect `worker_diff` during check-ins and record `team_review` before merging, relay contract changes across working siblings (`team_message` `worker`/`workers`/`all: true`), unblock technical questions immediately while leaving desk permission prompts to the owner, and sequence rebases before integrating with `team_merge`.
- **Out of scope.** Factory cloud workers get no office tools, as today.

## Inter-agent noise gate

With the Gemini Decisions API connected (Settings → Connections → Gemini Decisions API) and **Inter-agent noise gate & smart wakeup filter** on (`wakeFilterOn` in office-wide `gemini.json`, on by default), `src/server/wake-filter.ts` routes inter-agent traffic before it wakes anyone. Each message costs one `gemini-decision-1` call (2.5-second timeout, zero output tokens). The gate decides only **when** a lead or sibling is interrupted. What gets recorded stays the same: `team_status`, `team_wait`, `team_report_get`, `office_inbox` and the team board still show every report, held or not.

- **Gated channels.** `team_report` (never questions), a subagent's own `done` event, `lead_notify` with `kind: "update"`, `team_note` when at least one working sibling who has not reported would be interrupted, and non-urgent `visit_message` tells. Questions, `lead_notify` questions, blockers and tests, asks, handoffs, replies, urgent messages and owner or lead messages are never gated.
- **Context packet.** One scrubbed request (`redactGeminiSecrets`, at most 14,000 characters) carries what the lead waits on (its task, TodoWrite plan, status and last 30 terminal lines; the Orchestrator's own runtime, or a Grok Bot's identity), the team board (every teammate's status, task, areas, latest note and report, across open floors for building leads), the sender's chatter (routine updates without a new commit, PR, blocker or question in the last five minutes, and whether its pushed SHA changed), and the message with its artifacts. It asks a `traffic` choice, an independent `pure_chatter` noul, and for notes one `sib_N` noul per interruptible sibling (at most 12).
- **Decisions.** `wake_immediately` delivers as before. `hold_for_batch` records a completion as `gate: "held"` and wakes the lead once for the whole batch when no teammate is still starting or working (another teammate settling, leaving or being sent home), when news that does wake it arrives, or at the 10-minute ceiling. `record_silently` records it as `gate: "silent"`; it never wakes the lead, but the lead sees it at its next status read. `block_and_coach` returns coaching text to the sender instead of delivering.
- **Guardrails.** Deterministic rules force a wake, whatever the model says, for questions, unblockable kinds, urgent messages, `failed` or `blocked` results, merge conflicts, wording that asks the recipient to act ("need your decision", "please confirm", "ready for your merge", "can you…"), a `lead_notify` update or progress report announcing a pull request its sender has not announced before, and the last active teammate finishing. A quieter route needs at least 0.5 of the traffic probability, or the message wakes. A finished teammate is never just recorded while others work: it is held for the batch instead, and with nobody else working it wakes. Blocking needs both locks (`traffic` at least 0.85 and `pure_chatter` at least 0.88) on a message the guardrails allow: only a short `team_note`, `lead_notify` update or visit tell with no question mark, link, code span, file path, hash, measured result, issue or PR reference, problem or decision word, new edit areas, or artifacts. `team_report` and `done` events are always recorded, so a blocked answer for one is treated as quiet. Anything else the model picks as block is downgraded to `record_silently`.
- **Sibling notes.** A working sibling is interrupted by a note when its `sib_N` relevance is at least 0.60, or when the note names it, cites one of its declared areas, or declares an overlapping area. A missing answer notifies that sibling. A note the gate reads as routine still posts to the board but reaches only siblings it names or overlaps; a blocked note is not posted, and `team_note` answers with coaching text instead.
- **Grok Bots and Visits.** For a Grok Bot lead, woken events push at once; held and silent events queue and ride along with the next push. A routine `lead_notify` update is saved in `office_inbox` and returns `deferred: true` instead of pushing. Visits keep no store to hold a message in, so for a tell only `block_and_coach` changes anything; every other answer delivers it as before.
- **Fail-open.** With the toggle off, airgapped mode on, no key, a rejected key, an HTTP or network error, a timeout, a safety block or a thrown error, every message delivers exactly as before. Turning the gate off, disconnecting Gemini or switching to airgapped mode releases every held batch at once (`Team.flushHolds`), so no lead waits on a gate that no longer routes. Held events that were waiting when the office restarts lose their ceiling, so they come back unheld and wake the lead normally; silent ones stay silent (`gate` in `team.json`).
- **Telemetry.** The Gemini Settings section shows how many messages were evaluated, woken, held, recorded silently, blocked, sibling interrupts skipped and failed-open calls, plus the last latency. Calls, tokens and latency add to the same usage readout as Living 3D reactions.
- **Backtest.** `node --import tsx tools/backtest-wake-filter.mjs` replays real `droid_office` traffic from `~/.factory/sessions` and each floor's `team.json` through the gate (see [tools/AGENTS.md](../tools/AGENTS.md)).
## How the connection was chosen, and adding a tool

The spikes used the real installed `droid` **1.1.0**, a loopback HTTP MCP fixture and a fresh temporary `HOME` for each case. No model inference or changes to the owner's real Factory config were needed:

| Check (`droid exec --list-tools --output-format json -m glm-5.3-flash`) | Result |
| --- | --- |
| `--settings` containing `mcpServers`, literal or variable headers, `--only-tools MCP:office-spike` | Exit 1, unknown tool identifier, no HTTP request |
| Temporary `~/.factory/mcp.json`, variables set | Exit 0, `initialize` and `tools/list` received both expanded headers |
| Same profile, variables unset, ordinary tool listing | Exit 0, no MCP tools, no HTTP request |
| Shipped office wrapper and profile merger, `--only-tools MCP:droid-office` | Exit 0, `mcp_droid-office_office_whoami` allowed |

This matches [Droid's documented profile and header-expansion behavior](https://docs.factory.com/harness/mcp.md); URLs are literal, not variable-expanded. Real MCP HTTP clients also verified simultaneous callers, hidden direct-call refusals, live setting changes and revoked tokens. The installed-office clone rendered with all seven real floors, served `/` and `/dashboard`, refused anonymous `/office/mcp` calls, and removed/restored its profile entry when the setting changed.

The office needs only an HTTP handler and per-caller tool lists, so it uses the SDK directly rather than a framework on top of it; mcp-use, tried first, also installed an inspector and CLI (about 69 MiB) and needed Node 22.22.2. An isolated `npm install @modelcontextprotocol/server@2.3.1` adds 3 packages: `server` and `core` (**7.7 MiB**) and Zod (**8.1 MiB**). Zod was only a transitive dependency before; the office now depends on it directly for the tool schemas. The SDK needs Node 20 or later, the office's existing floor. The tests' client is `@modelcontextprotocol/client` **2.3.1**, a dev dependency.

Each module exports `instructions` and `register(server, deps)`. Register with `server.tool(definition, access, handler)`, where the definition contains its Zod object `inputSchema`. `access(caller)` returns `undefined` to allow or a readable refusal to hide and refuse the tool. Use `officeAccess.worker`, `.mayHire`, `.team`, `.subagent` or `.visits`. The handler receives `(args, caller, signal)`; `signal` aborts when the caller cancels or disconnects, and a tool must not record that the caller saw a result after that (`whiteboard_read` then moves no read points); `caller` holds the authenticated `worker`, its `floor` (workers, team, visits, Whiteboard), live `settings` and absolute working `cwd`, including multi-repository workspaces. `OfficeMcpDeps` supplies the settings and worker-to-floor resolver. Return `officeResult(text, structuredContent)` or `officeError(text)`, or MCP image content. Never resolve file paths against the server's cwd.

Each tool returns readable `content` text and, where useful, `structuredContent`. Worker, floor, Whiteboard card and question results (including `office_whoami`, `office_floors`, `office_inbox`, `office_roster`, `office_look`, `office_worker_*`, `team_hire`, `team_watch`, `team_status`, `team_message`, `team_review`, `worker_log`, `team_wait`, `team_report_get`, `questions_list`, and `whiteboard_*`, plus Grok Bot webhook items) include ready-made `deepLink` URLs (`http(s)://<tailscale-or-lan>:<port>/open/<kind>/<id>?...` when reachable, else `droidoffice://open/<kind>/<id>?...`, plus `questionDeepLink` when a worker is waiting on input and `floorDeepLink` on board reads) so leads and external bots can drop clickable Android links directly into chat without exposing any token. Errors are `isError` results with `structuredContent: {code, hint}` whose text says what to do next, never stack traces. HTTP authentication and malformed-request errors include `code` and `hint` alongside their existing body and unchanged 401/400 status.

Structured hires default to a fresh worktree; explicit `worktree: false` permits read-only checkout work without a base or branch. Floor workers select their own repository by absolute path; building agents must name an open repository by path, floor id or floor name. A requested branch must be new. `from` and `task.baseBranch` also accept `worker:<name or id>` or an absolute registered worktree path (active, dismissed-but-kept, or retained integration worktrees; canonical aliases accepted). These handoffs pin its current HEAD and add branch/commit provenance to the new brief and response. They never move the original worker or copy uncommitted files; a branch name remains a normal starting point.

`team_merge` integrates committed work into the lead's current branch or a named existing local target. Building agents must name `target`. It uses the target's existing worktree, or temporarily checks an unchecked-out target out without switching any existing checkout. Dirty targets, existing Git operations, self-targets and another worker's occupied checkout return a structured blocked result. Default cherry-picks apply non-merge commits after the worker's recorded base, oldest first, excluding commits and patch-equivalent changes already on the target; `commits` overrides that range with explicit ordered revisions. Success returns `status: ok`, a one-line landed summary and `artifacts` with commit/file provenance. Conflicts return `isError`, `status: blocked`, `conflicts` (paths and hunks with `header`, `ours`, `theirs`, plus index stages), and `remaining` with the exact worktree and Git continue/abort commands. Only actually conflicted temporary worktrees stay for resolution; non-conflict failures abort or quit Git state and remove temporary worktrees, including failed worktree creation. Non-conflict failures report `failed`, or `partial` if earlier cherry-picks landed. The target's current HEAD is always included after an attempted integration. `artifacts.mergeCommit` appears only for a merge that advances the target, never a no-op or cherry-pick. PR creation verifies local HEAD against origin's actual remote branch, defaults its base to the worker's recorded starting branch then the floor branch, and records the PR on the live/persisted worker card and refreshes the board. PR success returns the same result status/summary with `artifacts.prUrl` and `prNumber`, through the floor's existing forge.

Pruning checks ownership and dirty state, then stops the worker and asks Git to remove the worktree without force. A race that makes it dirty leaves it on disk and returns an error. Detached worktrees stay until their commits are on a branch. Safe branch deletion may leave a pre-existing or unmerged branch; it never deletes a remote branch.

For building agents, team-management tools accept `floor?`, an open floor's id,
name or checkout path; without it, status includes teams across all open floors.
A name two open floors share is refused with their ids, and so is a hire whose
`floor` and `task.repo` name different floors. Worker names must be unambiguous,
or use a worker id. A `since` cursor names its floor (`team:<floor>:<seq>`); a
bare sequence number is only for a floor worker, whose floor is known. A bot's
status reads do not consume reports: acknowledge them through `office_inbox`.
Building agents have no current floor: hiring always names one. Local workers
keep their own floor's scope and terminal delivery.

## Code layout

- `src/server/office-mcp/index.ts`: the server, its `instructions`, auth, per-caller filtering, the mount on the hook server, and the Droid connection config.
- `src/server/office-mcp/team.ts`, `team-events.ts` (structured status helpers, `team_wait`, `team_report_get`, `questions_list`, `question_answer`), `whiteboard.ts`, `visits.ts`: one module per area, each exporting a `register(server, deps)` function. Each owns its tools' descriptions and its slice of the instructions.
- `owner.ts`: roster, terminal reads, dismissal and common owner results; `owner-tools.ts`: focused tool registry and routing; `owner-schemas.ts`: shared validated inputs. Tests assert the exact external tools/list, refusal of removed tools and retained worker-action routing, without a generic gateway.
- Tests: `tests/office-mcp*.test.ts`, calling tools through a real MCP client against the mounted server.
