# User Taste
- Works on an Apple M5 Pro with 48GB unified memory — keep asset/render/loop budgets sized for this machine. Confidence: 0.85
- Uses blender-mcp for 3D asset generation work (e.g. regenerating assets in "agent-office" projects). Confidence: 0.8
- Sets explicit performance budgets for asset work (e.g. "do not degrade performance by more than 50%") and expects swaps/replacements to be done in place. Confidence: 0.75
- Prefers autonomous long-running execution: gives a target (e.g. "keep going until at least 25 assets") and expects the agent to keep iterating without check-ins until the quota is met. Confidence: 0.8
- Wants work verified in the actually-running app: launch the real app and take a screenshot as proof, not just automated tests/builds passing. Their own screenshot from the live app counts as sign-off — accept it as the fix being proven, then run the test suite and push the PR instead of re-shooting it yourself. Confidence: 0.8
- Expects delivery as a pull request: the agent should branch, commit, push and open a PR as the final artifact, with visual evidence (screenshots) embedded. Confidence: 0.75
- Gives feedback as a screenshot plus one terse caption (typos included) rather than a written bug description — read the image as the primary signal. Confidence: 0.7
- Holds generated/procedural asset swaps to runtime contracts, not just visual fidelity: anything that moves, rotates or is referenced by index must keep its origin, facing and child structure, and should be verified in the live scene. Confidence: 0.75
- States a hypothesis loosely and may self-correct it moments later ("you just had the initial positions wrong, I think") — take the narrow root cause seriously instead of accepting or over-correcting the broader framing, and say plainly what the actual cause was. Confidence: 0.7
- Prefers attaching to their already-running browser (live Chrome) over a scripted/headless screenshot rig once a specific view is hard to frame; stop iterating on automated camera moves and drive the session they already have open. Confidence: 0.6
- Checks whether work actually landed, not whether it looks done — calls it out bluntly ("u didnt change anything") when an agent claims a fix is proven while the changes are still uncommitted. Never treat a screenshot or a passing build as proof that the shipped/delivered state changed. Confidence: 0.8
- Distinguishes "edited locally" from "shipped": expect git-level verification (branch, `git status`, commits ahead of origin, checksums/diffs of changed binaries) before asserting a fix is done or the PR carries it. Confidence: 0.75
- When an agent's stated conclusion is contradicted ("u didnt change anything"), the correct response is to go measure the actual state immediately and admit the overclaim, not to defend it or repeat the earlier reasoning. Confidence: 0.7
- Will stop the agent cold with "Do you understand what the actual issue is?" when a fix is being driven by an unconfirmed hypothesis — expects the real root cause to be named and agreed on before more edits land, not a series of speculative changes. Restate the problem, confirm it, then act. Confidence: 0.65
- Prefers assets sized to the consuming code's real numbers (e.g. derive furniture dimensions from the character capsule radius in source) rather than generic real-world proportions; validate clearances with measurements/geometry queries instead of eyeballing renders. Confidence: 0.65
